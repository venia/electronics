Шаги в CubeMX (только Pinout, код пока не генерируем)

1. New Project → MCU Selector → STM32H723VGT6 → Start Project
2. RCC → HSE = Crystal/Ceramic Resonator (на плате реальный кварц 25 МГц)
3. SYS → Debug = Serial Wire
4. Connectivity → SPI2 → Mode = Full-Duplex Master, затем проверить, что CubeMX реально выбрал PB13/14/15 (а не другой альтернативный набор пинов SPI2)
— если нет, кликнуть по каждому пину на картинке чипа и выбрать вручную
5. Клик по PC0, PC1, PC2, PC3 → GPIO_Output
6. Клик по PC4 → GPIO_Output, PC5 → GPIO_Input
7. User Label для каждого: LCD_CS, LCD_DC, LCD_RST, LCD_BL, TP_CS, TP_IRQ — без суффикса _Pin (иначе получится задвоение, как уже было в Project1)
8. PC0-PC4: Output Push Pull, Low/Medium speed; PC5: Input, Pull-up
9. Убедиться, что ни один пин не подсвечен как конфликтующий
10. Save Project as… → в папку STM32-1-ANALYZE. Generate Code пока не нажимать.

Core/Src/syscalls.c, sysmem.c   — заглушки для printf/malloc (стандартная библиотека C)

Важный принцип: всё, что мы напишем сами, нужно писать только между строками /* USER CODE BEGIN ... */ и /* USER CODE END ... */. 
Если снова открыть .ioc и нажать Generate Code — CubeMX перезапишет весь файл заново, но код между этими маркерами сохранит. Всё, 
что вне их — сгенерировано и будет затёрто.

Core/Src/main.c — по порядку выполнения

Порядок вызовов в main() (main.c:68-110):
1. MPU_Config() — настраивает Memory Protection Unit. Сейчас там только запрет доступа к нулевому адресу памяти (защита от разыменования NULL-указателя) 
— стандартная заготовка CubeMX, не наше.
2. HAL_Init() — сбрасывает периферию в известное состояние, включает SysTick на 1мс тик.
3. SystemClock_Config() — здесь настоящая настройка тактирования (разберём ниже).
4. MX_GPIO_Init() и MX_SPI2_Init() — включают конкретно нужные нам пины и SPI2.
5. while(1) {} — бесконечный пустой цикл. Сюда мы добавим наш тест.

SystemClock_Config() (main.c:116-169) — то, что мы настраивали в Clock Configuration:
- HAL_PWREx_ConfigSupply + VOLTAGESCALING_CONFIG(SCALE1) — питание ядра на максимальную производительность (нужно для 400 МГц)
- RCC_OscInitStruct.PLL.PLLSource = RCC_PLLSOURCE_HSE — источник PLL это внешний кварц 25 МГц
- PLLM=2, PLLN=32, PLLP=1 — делители PLL: 25МГц / 2 = 12.5МГц (вход VCO) × 32 = 400МГц (выход)
- RCC_ClkInitStruct... — как эти 400 МГц раздаются по шинам (AHB/2=200, APB/2=100 и т.д.)
- FLASH_LATENCY_2 — количество тактов ожидания при чтении Flash-памяти на этой частоте (чем выше частота, тем больше "wait states" нужно — CubeMX 
посчитал это сам)

MX_SPI2_Init() (main.c:176-217) — настройка самого SPI2:
- Mode=SPI_MODE_MASTER, Direction=SPI_DIRECTION_2LINES — полный дуплекс (SCK+MOSI+MISO)
- DataSize=SPI_DATASIZE_8BIT — 8 бит на посылку (то, что мы поправили)
- CLKPolarity=LOW, CLKPhase=1EDGE — режим SPI Mode 0 (самый распространённый)
- NSS=SPI_NSS_SOFT — аппаратный вывод CS не используется, мы дёргаем CS сами через обычный GPIO (LCD_CS/TP_CS)
- BaudRatePrescaler=32 — 6.25 МБит/с (то, что мы поправили)
- Остальные поля (NSSPMode, MasterSSIdleness, FifoThreshold...) — это новые для H7 параметры, но раз NSS=SOFT (мы управляем CS вручную), они физически
 не используются, можно не задумываться о них

MX_GPIO_Init() (main.c:224-265) — важный нюанс, на который надо обратить внимание:
HAL_GPIO_WritePin(GPIOC, LCD_CS_Pin|LCD_DC_Pin|LCD_RST_Pin|LCD_BL_Pin|TP_CS_Pin, GPIO_PIN_RESET);
Это выполняется до того, как пины физически настроены на выход — задаётся исходное состояние (LOW), а потом уже конфигурируется режим. Значит при старте 
все 5 пинов будут LOW: LCD_CS=0 (экран выбран), LCD_DC=0 (режим команды), LCD_RST=0 (экран в сбросе!), LCD_BL=0 (подсветка скорее всего выключена, 
судя по официальному Arduino-драйверу — там подсветка управляется через analogWrite и включается ненулевым значением, то есть активна по HIGH). 
Это нормальная отправная точка — RST=0 держит контроллер в сбросе, пока мы явно не отпустим его в нашем коде.

Core/Src/stm32h7xx_hal_msp.c — вторая половина конфигурации периферии

Это не дублирование main.c. HAL использует паттерн "MSP" (MCU Support Package): когда мы вызываем HAL_SPI_Init(&hspi2), он сам внутри себя вызывает 
функцию HAL_SPI_MspInit(hspi) — а она определена именно тут. Здесь:
- Включается тактирование для SPI2 (__HAL_RCC_SPI2_CLK_ENABLE) и его источник (RCC_SPI123CLKSOURCE_PLL)
- Настраиваются PB13/14/15 не как простой GPIO, а как Alternate Function (GPIO_MODE_AF_PP, GPIO_AF5_SPI2) — это отдельный режим, где пином управляет 
не программа напрямую, а периферия SPI2

То есть: обычные GPIO (LCD_CS и т.п.) настраиваются в main.c → MX_GPIO_Init(), а пины, которые "принадлежат" периферии (SPI-шина), настраиваются в 
отдельном stm32h7xx_hal_msp.c. Так генерирует CubeMX всегда — это не ошибка и не наше решение.

Core/Src/stm32h7xx_it.c

Обработчики исключений процессора (HardFault_Handler и т.п.) — сейчас это просто "зависнуть в бесконечном цикле", если что-то пошло совсем не так на 
уровне процессора (например, обращение по неверному адресу). SysTick_Handler вызывает HAL_IncTick() — это то, что даёт работать HAL_Delay() и 
HAL_GetTick().

Остальное (коротко)

- system_stm32h7xx.c — вызывается ещё до main() (из ассемблерного стартапа), включает FPU и минимальный бутстрап чипа
- syscalls.c/sysmem.c — заглушки, чтобы линковщик не ругался, если где-то в коде появится printf/malloc (мы их пока не используем)
- startup_stm32h723vgtx.s — таблица векторов прерываний + код, который выполняется первым: настраивает стек, копирует .data из Flash в RAM, 
зануляет .bss, зовёт SystemInit(), потом main()
- .ld файлы — описывают физическую карту памяти (где Flash, где какая RAM), стек 0x400 байт и куча 0x200 байт (видно в .ioc: 
ProjectManager.StackSize/HeapSize)

ЧАСТЬ 2. Что тестируют в первую очередь на новом экране

Стандартный "hello world" для любого TFT — это не текст и не картинка, а заливка всего экрана сплошным цветом, обычно циклически 
(красный → зелёный → синий → повтор). Причина: это самый простой тест, который проверяет разом всю цепочку — SPI физически работает, контроллер
 экрана принял команды инициализации и понимает адресацию окна вывода на всю площадь матрицы. Если хоть один пиксель не докрашен или показывает 
 "снег" — сразу видно, где искать баг (адресация окна, размер буфера, скорость SPI).

Я посмотрел (свежим взглядом, не из старого проекта) на уже проверенный тобой на Ардуино официальный драйвер (Arduino\LCD_Show\LCD_Driver.cpp) — 
именно так это делает и он: LCD_Init() → LCD_Clear(color). Возьмём оттуда протокол SPI и порядок регистров инициализации ILI9486 (это официальный, 
подтверждённо рабочий у тебя код — прямой источник, а не предположения).

Что выяснилось из чтения этого файла (важно для нашего драйвера):
- Команда (регистр) шлётся как ровно 1 байт, CS дёргается вокруг каждой отдельной посылки
- Параметр шлётся как 2 байта: LCD_WriteData(uint16_t Data) шлёт Data>>8 затем Data&0xFF — то есть для обычного 8-битного параметра типа 0x19 это 
будет 0x00, 0x19
- Сброс: RST→HIGH, 500мс, RST→LOW, 500мс, RST→HIGH, 500мс
- После длинного списка регистров производителя (gamma/питание матрицы — эти магические числа мы просто копируем, они не имеют "логического" объяснения, 
это заводская подстройка от Waveshare) идёт: 0x3A=0x55 (формат пикселя 16 бит RGB565), 0x36=0x28 (ориентация, режим D2U_L2R — который и используется
 в проверенном тобой примере по умолчанию), 0x11 (Sleep Out) + пауза 120мс, 0x29 (Display On)
- Заливка: 0x2A/0x2B (задать прямоугольное окно X/Y) → 0x2C (начать запись в GRAM) → отправить нужное число пикселей, каждый 2 байта (RGB565), 
не отпуская CS между пикселями одной заливки

Новые файлы, которые добавляю

Core/Inc/lcd_ili9486.h — интерфейс: что можно вызвать из main.c (LCD_Init(), LCD_FillScreen()), размеры экрана, готовые цвета в формате RGB565.

Core/Src/lcd_ili9486.c — реализация:
- LCD_CS_Low/High — обёртки над HAL_GPIO_WritePin для ножки LCD_CS
- LCD_WriteReg(reg) — DC=0 (команда), CS=0, отправить 1 байт по SPI, CS=1
- LCD_WriteData8(data) — DC=1 (данные), CS=0, отправить 2 байта (0x00, значение) — именно та асимметрия протокола, о которой выше
- LCD_Reset() — аппаратный сброс, ровно как в проверенном драйвере (500/500/500 мс)
- LCD_InitRegisters() — тот самый список регистров производителя, построчно как в оригинале, только сразу с финальными значениями 0xB6/0x36 (в оригинале 
Waveshare сначала пишет туда "черновое" значение, а через несколько строк перезаписывает правильным — я сразу пишу правильное, результат идентичен, 
лишней записи нет смысла повторять)
- LCD_Init() — включает подсветку (LCD_BL → HIGH, важно: сейчас после MX_GPIO_Init() она в LOW, то есть выключена, пока мы явно не включим), делает
 сброс, шлёт регистры инициализации, Sleep Out, Display On
- LCD_SetWindow(xs,ys,xe,ye) — задаёт прямоугольную область для следующей записи в GRAM
- LCD_FillScreen(color) — строит одну строку буфера (480 пикселей × 2 байта = 960 байт) один раз, затем 320 раз отправляет её по SPI без отпускания 
CS — заливка всего экрана

Правки в main.c (только внутри USER CODE секций):
- #include "lcd_ili9486.h" в Includes
- LCD_Init(); в USER CODE BEGIN 2 (после MX_SPI2_Init(), до while)
- В while(1): циклическая заливка красный → зелёный → синий с задержкой 1 сек — если увидим на экране эти три цвета по очереди, значит вся цепочка 
SPI → ILI9486 → GRAM работает правильно.
