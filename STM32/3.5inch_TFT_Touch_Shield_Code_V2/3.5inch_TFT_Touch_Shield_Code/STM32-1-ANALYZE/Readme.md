# STM32H723VGT6 + Waveshare 3.5" TFT Touch Shield (без графического фреймворка)

Проект (с нуля): подключить Waveshare 3.5" TFT Touch Shield (ILI9486, 480x320, резистивный тач
XPT2046) к плате **WeAct Studio Mini STM32H723VGT6** по SPI, чистым HAL/регистрами, без TouchGFX/LVGL.

Среда: STM32CubeMX (отдельное приложение) + STM32CubeIDE 2.2.0.

## Статус на старте

- Питание проверено: экран подключён, светится ровным белым по всей площади через шлейф →
  подсветка и питание модуля исправны (см. `my_project1.jpg`).
- Контакты уже распаяны согласно таблице ниже (см. `ESP-GPIO.jpg`).
- Ардуино-референс проверен и работает "из коробки": `Arduino\LCD_Show` и `Arduino\LCD_Touch`
  из официального пакета Waveshare (`3.5inch_TFT_Touch_Shield_Code_V2\...\Arduino\`).

### Waveshare 3.5" TFT Touch Shield — какие сигналы нужны

9 сигналов (без SD-карты и TP_BUSY — они не критичны для старта):
SCLK, MISO (для тача), MOSI, LCD_CS, LCD_DC, LCD_RST, LCD_BL, TP_CS, TP_IRQ.

## Шаги в STM32CubeMX (планирование пинов)

Цель этого прохода — только Pinout & базовый System Core, **без** генерации кода. Генерацию кода и
тонкую настройку Clock Tree делаем отдельным шагом после того, как пины подтверждены.

**Прогресс:**
- [x] 1. Создание проекта (STM32H723VGT6)
- [x] 2. RCC → HSE Crystal/Ceramic Resonator
- [x] 3. Trace and Debug → DEBUG = Serial Wire (подтверждено скриншотом: PA13/PA14 зелёные,
      DEBUG_JTMS-SWDIO/DEBUG_JTCK-SWCLK)
- [x] 4. SPI2 = Full-Duplex Master, пины вручную переназначены на PB13(SCK)/PB14(MISO)/PB15(MOSI)
      (подтверждено скриншотом от 2026-09-06 — все три зелёные с правильными подписями)
- [x] 5-8. GPIO для LCD/тача настроены и подписаны (подтверждено скриншотом от 2026-09-06: PC0=LCD_CS,
      PC1=LCD_DC, PC2=LCD_RST, PC3=LCD_BL, PC4=TP_CS — все Output Push-Pull/No pull/Low speed;
      PC5=TP_IRQ — Input/Pull-up)
- [x] 9-10. Конфликтов нет, проект сохранён и сгенерирован: `STM32H723VGT6-Waveshare\` (CubeMX 6.18.0,
      FW_H7 V1.13.0)
- [x] **Clock Configuration:** PLL Source = HSE (кварц 25 МГц), M=2/N=32/P=1 → SYSCLK = **400 МГц**,
      AXI/HCLK3 = 200 МГц, APB1/APB2 = 100 МГц (подтверждено в `.ioc` после перегенерации)
- [x] **SPI2 Configuration:** Data Size = **8 Bits**, Baud Rate Prescaler = **/32 → 6.25 МБит/с**
      (безопасная стартовая скорость; точную скорость для ILI9486/XPT2046 подберём экспериментально)

CubeMX-этап пройден полностью. Импорт в STM32CubeIDE и первый тестовый билд пустого проекта —
успешно (подтверждено пользователем).

## Разбор сгенерированного кода (что где и зачем, до наших правок)

### Структура проекта

```
Core/Inc/main.h                 — объявления пинов, прототипы
Core/Inc/stm32h7xx_it.h         — прототипы обработчиков прерываний
Core/Inc/stm32h7xx_hal_conf.h   — какие модули HAL включены (SPI, GPIO, RCC...)
Core/Src/main.c                 — точка входа, конфигурация тактирования и периферии
Core/Src/stm32h7xx_hal_msp.c    — низкоуровневая настройка GPIO/тактирования ПОД периферию
Core/Src/stm32h7xx_it.c         — обработчики прерываний (исключения CPU + SysTick)
Core/Src/system_stm32h7xx.c     — самая ранняя инициализация чипа (до main())
Core/Src/syscalls.c, sysmem.c   — заглушки для printf/malloc (стандартная библиотека C)
Core/Startup/startup_...s       — ассемблер: таблица векторов, запуск CPU
Drivers/                        — библиотеки ST (HAL + CMSIS), не трогаем
STM32H723VGTX_FLASH.ld/_RAM.ld  — linker-скрипты (карта памяти)
STM32H723VGT6-Waveshare.ioc     — файл CubeMX, источник истины для всей этой генерации
```

Ключевой принцип: свой код пишем только между `/* USER CODE BEGIN ... */` и `/* USER CODE END ... */`.
Всё, что вне этих маркеров — сгенерировано CubeMX и будет затёрто при повторной генерации из `.ioc`.

### `Core/Src/main.c` — порядок выполнения

`main()` (main.c:68-110) вызывает по порядку:
1. `MPU_Config()` — настраивает Memory Protection Unit; сейчас только запрет доступа к нулевому адресу
   (защита от разыменования NULL) — стандартная заготовка CubeMX
2. `HAL_Init()` — сбрасывает периферию, включает SysTick на 1мс тик
3. `SystemClock_Config()` — настоящая настройка тактирования (см. ниже)
4. `MX_GPIO_Init()` и `MX_SPI2_Init()` — включают наши пины и SPI2
5. `while(1) {}` — бесконечный цикл (сюда добавлен наш тест, см. следующий раздел)

**`SystemClock_Config()` (main.c:116-169)**:
- `HAL_PWREx_ConfigSupply` + `VOLTAGESCALING_CONFIG(SCALE1)` — питание ядра на максимум (нужно для 400 МГц)
- `PLLSource = RCC_PLLSOURCE_HSE` — источник PLL это внешний кварц 25 МГц
- `PLLM=2, PLLN=32, PLLP=1` — 25МГц/2=12.5МГц (вход VCO) × 32 = 400МГц (выход)
- `RCC_ClkInitStruct` — как 400 МГц раздаются по шинам (AHB/2=200, APB/2=100)
- `FLASH_LATENCY_2` — число тактов ожидания при чтении Flash на этой частоте (посчитано CubeMX)

**`MX_SPI2_Init()` (main.c:175-216)**:
- `Mode=MASTER`, `Direction=2LINES` — полный дуплекс (SCK+MOSI+MISO)
- `DataSize=8BIT`, `CLKPolarity=LOW`, `CLKPhase=1EDGE` — SPI Mode 0, байт за раз
- `NSS=SOFT` — аппаратный CS не используется, CS дёргаем вручную через обычный GPIO
- `BaudRatePrescaler=32` → 6.25 МБит/с
- Остальные поля (`NSSPMode`, `MasterSSIdleness`, `FifoThreshold`...) — новые для H7 параметры,
  не влияют на нас, т.к. NSS=SOFT

**`MX_GPIO_Init()` (main.c:223-264)** — важный нюанс:
```c
HAL_GPIO_WritePin(GPIOC, LCD_CS_Pin|LCD_DC_Pin|LCD_RST_Pin|LCD_BL_Pin|TP_CS_Pin, GPIO_PIN_RESET);
```
Выполняется до перевода пинов в режим выхода — задаёт исходное состояние. Значит **при старте все 5
выходов LOW**: LCD_CS=0 (экран выбран), LCD_DC=0 (режим команды), LCD_RST=0 (**экран в сбросе**),
LCD_BL=0 (подсветка выключена — судя по официальному Arduino-драйверу, активна по HIGH). Нормальная
отправная точка — сброс держится, пока код явно его не отпустит.

Также видно `HAL_SYSCFG_AnalogSwitchConfig(...PC2/PC3...CLOSE)` — не ошибка, а особенность H723:
у PC2/PC3 есть доп. площадка (PC2_C/PC3_C), CubeMX сам корректно подключает её при использовании
этих пинов как GPIO.

### `Core/Src/stm32h7xx_hal_msp.c` — вторая половина конфигурации периферии

Не дублирование `main.c`. HAL использует паттерн "MSP" (MCU Support Package): когда вызывается
`HAL_SPI_Init(&hspi2)`, он сам внутри вызывает `HAL_SPI_MspInit(hspi)` — а она определена именно
здесь. Тут:
- включается тактирование SPI2 и его источник (`RCC_SPI123CLKSOURCE_PLL`)
- PB13/14/15 настраиваются **не** как простой GPIO, а как **Alternate Function**
  (`GPIO_MODE_AF_PP`, `GPIO_AF5_SPI2`) — этим пином управляет периферия SPI2, а не программа напрямую

Правило: обычные GPIO (LCD_CS и т.п.) — в `main.c → MX_GPIO_Init()`; пины, "принадлежащие" периферии
(шина SPI) — в отдельном `stm32h7xx_hal_msp.c`. Так CubeMX генерирует всегда, это не наше решение.

### `Core/Src/stm32h7xx_it.c`

Обработчики исключений процессора (`HardFault_Handler` и т.п.) — сейчас просто бесконечный цикл,
если что-то пошло не так на уровне CPU (например обращение по неверному адресу).
`SysTick_Handler` вызывает `HAL_IncTick()` — от этого зависят `HAL_Delay()` и `HAL_GetTick()`.

### Остальное (коротко)

- **`system_stm32h7xx.c`** — вызывается ещё до `main()` из ассемблерного стартапа, включает FPU и
  минимальный бутстрап чипа
- **`syscalls.c`/`sysmem.c`** — заглушки, чтобы линковщик не ругался, если появится `printf`/`malloc`
- **`startup_stm32h723vgtx.s`** — таблица векторов + код, который выполняется первым: стек, копирование
  `.data` из Flash в RAM, зануление `.bss`, вызов `SystemInit()`, затем `main()`
- **`.ld` файлы** — карта памяти (Flash/RAM), стек 0x400 байт и куча 0x200 байт
  (см. `ProjectManager.StackSize/HeapSize` в `.ioc`)

## Первый тест экрана: заливка цветом (без фреймворка)

Стандартный "hello world" для TFT — это не текст и не картинка, а **заливка всего экрана сплошным
цветом**, обычно циклически (красный → зелёный → синий → повтор). Это самый простой тест, который
разом проверяет всю цепочку: SPI физически работает, контроллер экрана принял регистры инициализации
и правильно понимает адресацию окна вывода на всю площадь матрицы. Если хоть один пиксель не
докрашен или виден "снег" — сразу понятно, где искать баг (адресация окна, размер буфера, скорость
SPI), в отличие от сразу сложного UI.

Протокол SPI и порядок регистров инициализации ILI9486 взяты из официального, уже проверенного
пользователем на Arduino драйвера `Arduino\LCD_Show\LCD_Driver.cpp` (`LCD_Init()` → `LCD_Clear()`) —
то есть из подтверждённо рабочего источника, а не предположений. Из чтения этого файла выяснилось:
- команда (регистр) шлётся как ровно **1 байт**, CS дёргается вокруг каждой отдельной посылки
- параметр шлётся как **2 байта**: `LCD_WriteData(uint16_t Data)` шлёт `Data>>8` затем `Data&0xFF` —
  для обычного 8-битного параметра типа `0x19` это будет `0x00, 0x19`
- сброс: RST→HIGH, 500мс, RST→LOW, 500мс, RST→HIGH, 500мс
- после длинного списка регистров производителя (gamma/питание матрицы — магические числа без
  логического объяснения, заводская подстройка Waveshare) идёт: `0x3A=0x55` (формат пикселя 16 бит
  RGB565), `0x36=0x28` (ориентация D2U_L2R — используется в проверенном примере по умолчанию),
  `0x11` (Sleep Out) + пауза 120мс, `0x29` (Display On)
- заливка: `0x2A`/`0x2B` (прямоугольное окно X/Y) → `0x2C` (начать запись в GRAM) → нужное число
  пикселей по 2 байта (RGB565), CS не отпускается между пикселями одной заливки

### Добавленные файлы

**`Core/Inc/lcd_ili9486.h`** — публичный интерфейс: `LCD_Init()`, `LCD_FillScreen(color)`, размеры
экрана (480×320), готовые цвета в формате RGB565.

**`Core/Src/lcd_ili9486.c`** — реализация:
- `LCD_CS_Low/High` — обёртки над `HAL_GPIO_WritePin` для ножки LCD_CS
- `LCD_WriteReg(reg)` — DC=0 (команда), CS=0, отправить 1 байт по SPI, CS=1
- `LCD_WriteData8(data)` — DC=1 (данные), CS=0, отправить **2 байта** (`0x00`, значение) — асимметрия
  протокола, описанная выше
- `LCD_Reset()` — аппаратный сброс, ровно как в проверенном драйвере (500/500/500 мс)
- `LCD_InitRegisters()` — список регистров производителя, построчно как в оригинале; только сразу с
  финальными значениями `0xB6`/`0x36` (в оригинале Waveshare сначала пишет туда "черновое" значение,
  через несколько строк перезаписывает правильным — здесь сразу пишется правильное, результат
  идентичен, повторять лишнюю запись смысла нет)
- `LCD_Init()` — включает подсветку (`LCD_BL` → HIGH; после `MX_GPIO_Init()` она в LOW, то есть
  выключена, пока явно не включим), делает сброс, шлёт регистры инициализации, Sleep Out, Display On
- `LCD_SetWindow(xs,ys,xe,ye)` — задаёт прямоугольную область для следующей записи в GRAM
- `LCD_FillScreen(color)` — строит одну строку буфера (480 пикселей × 2 байта = 960 байт) один раз,
  затем 320 раз отправляет её по SPI без отпускания CS — заливка всего экрана

Правки в `main.c` (только в USER CODE секциях):
- `#include "lcd_ili9486.h"`
- `LCD_Init();` после `MX_SPI2_Init()`
- В `while(1)`: циклическая заливка красный → зелёный → синий, по 1 секунде каждый — если все три цвета
  видны на всей площади экрана без артефактов, SPI-цепочка и инициализация ILI9486 работают правильно.

**Важно:** `MX_GPIO_Init()` ставит все выходы (включая LCD_BL) в LOW при старте — значит подсветка
гаснет сразу после сброса, пока `LCD_Init()` явно не включит её (`LCD_BL` → HIGH, активный уровень
подтверждён из официального Arduino-драйвера).

### Следующий шаг

В STM32CubeIDE: `ПКМ на проекте → Refresh (F5)` (чтобы IDE подхватила два новых файла, добавленных
напрямую в файловую систему), затем Build, затем прошивка через DFU — и смотрим, появляются ли на
экране красный/зелёный/синий по очереди.

1. **Создание проекта**
   - Открыть STM32CubeMX (отдельная программа — в CubeIDE 2.2.0 конфигуратор пинов вынесен наружу)
   - `File → New Project` → вкладка **MCU Selector** → в поиске ввести `STM32H723VGT6` → выбрать чип
     (корпус LQFP100) → **Start Project**

2. **System Core → RCC**
   - High Speed Clock (HSE): **Crystal/Ceramic Resonator** (на плате WeAct реальный кварц 25 МГц)
   - Low Speed Clock (LSE), если нужен RTC в будущем: Crystal/Ceramic Resonator (можно пропустить сейчас)

3. **Trace and Debug → DEBUG** (не в System Core → SYS — в этой версии CubeMX Debug вынесен в отдельную
   категорию "Trace and Debug" в списке слева; SYS теперь содержит только Timebase Source)
   - Mode: **Serial Wire** (оставляет SWDIO/SWCLK для отладчика, не даёт CubeMX случайно занять эти пины
     чем-то другим). Часто это уже стоит по умолчанию — проверить, что PA13/PA14 подсвечены как
     зарезервированные на картинке чипа справа.

4. **Connectivity → SPI2**
   - Mode: **Full-Duplex Master** (не "Transmit Only" — тачу XPT2046 нужен приём данных по MISO)
   - После выбора режима CubeMX подсветит пины на картинке чипа. **Обязательно проверить**, что это
     именно PB13 (SCK) / PB14 (MISO) / PB15 (MOSI) — у SPI2 на H723 есть несколько альтернативных
     наборов пинов, CubeMX может по умолчанию предложить не тот набор.
   - Если подсветились не те пины — кликнуть вручную на PB13 на картинке чипа → в выпадающем списке
     выбрать `SPI2_SCK`, аналогично PB14 → `SPI2_MISO`, PB15 → `SPI2_MOSI`.
   - Если снять с пина назначение SPI (например убрать SCK с неправильного пина) — CubeMX может
     автоматически перевести весь Mode в Disable и заодно освободить MOSI/MISO тоже. Это нормально:
     просто заново выставь Mode = Full-Duplex Master и назначь все три пина заново на правильные ноги.
   - Data Size, Prescaler, CPOL/CPHA на этом шаге **не трогать** — это Configuration, настроим на этапе
     программирования (сейчас по умолчанию стоит Data Size = 4 Bits — это тоже поправим позже, нужно
     будет 8 Bits).

5. **GPIO для управляющих линий дисплея**
   - Кликнуть на PC0 на картинке чипа → `GPIO_Output`
   - PC1 → `GPIO_Output`
   - PC2 → `GPIO_Output`
   - PC3 → `GPIO_Output`

6. **GPIO для тача**
   - PC4 → `GPIO_Output` (CS тача)
   - PC5 → `GPIO_Input` (IRQ тача — пока просто вход, без EXTI/прерывания; опрашивать вручную)

7. **Подписать пины** (System Core → GPIO, вкладка со списком пинов, поле **User Label**)
   - PC0 → `LCD_CS`
   - PC1 → `LCD_DC`
   - PC2 → `LCD_RST`
   - PC3 → `LCD_BL`
   - PC4 → `TP_CS`
   - PC5 → `TP_IRQ`
   - **Важно:** вписывать имя БЕЗ суффикса `_Pin` (например `LCD_CS`, а не `LCD_CS_Pin`) — CubeMX сам
     добавит `_Pin`/`_GPIO_Port` при генерации. Если вписать суффикс вручную, получится задвоение
     (`LCD_CS_Pin_Pin`).

8. **GPIO Mode/Speed для этих пинов** (там же, вкладка GPIO, после клика на конкретный пин)
   - PC0-PC4: **Output Push Pull**, No pull-up/pull-down, **Low** или **Medium** speed (не нужна высокая
     скорость фронтов для CS/DC/RST/BL — меньше звона/помех на проводах)
   - Начальный уровень (GPIO output level) можно оставить по умолчанию — реальную полярность
     (какой уровень означает "активно": LOW или HIGH, особенно для LCD_BL и LCD_RST) уточним
     экспериментально на этапе программирования
   - PC5 (TP_IRQ): **Input**, можно включить **Pull-up** (чтобы вход не "плавал", если провод IRQ
     физически не подключён)

9. **Проверка конфликтов**
   - Убедиться, что ни один из пинов PB13/PB14/PB15/PC0-PC5 не подсвечен CubeMX как уже занятый другой
     периферией — на этой плате они свободны (см. таблицу "занятая периферия" выше)

10. **Сохранить проект, код пока не генерировать**
    - `File → Save Project as…` → указать папку `STM32-1-ANALYZE`
    - `Project Manager` → можно уже сейчас проставить Project Name / Location, но кнопку
      **Generate Code** пока не нажимать — сначала проверяем план пинов вместе

## Диагностика: белый экран не пропадает (сессия 2026-09-07)

### Симптом

После первого теста заливки (`LCD_Init()` + циклическая `LCD_FillScreen()` красный/зелёный/синий)
экран остаётся ровным белым по всей площади — ни один из трёх цветов не появляется. Подсветка
горит, значит МК стартует и код доходит как минимум до `LCD_Init()`. На Arduino официальный пример
Waveshare (`Arduino/LCD_Show`) с этим же физическим экраном работает без проблем.

### Проверено и подтверждено рабочим (не источник бага)

- Протокол инициализации ILI9486 в `Core/Src/lcd_ili9486.c` сверен побайтово с двумя независимыми
  официальными источниками Waveshare из этого же пакета:
  - `Arduino/LCD_Show/LCD_Driver.cpp` (проверенно работает на реальном экране)
  - `STM32/XNUCLEO-F103RB/lcd3in5-demo/User/LCD/LCD_Driver.c` (официальный bare-metal STM32-демо
    от Waveshare, HAL-based, реальное железо STM32F103)

  Порядок регистров инициализации, деление параметра на 2 байта (`0x00`, значение), тайминги сброса
  (500/500/500 мс), значения MADCTL(0x36)=0x28 и 0xB6=0x62 для сканирования D2U_L2R — везде совпадают
  один в один. То есть сама последовательность регистров ILI9486 — не "угадана", а подтверждена двумя
  независимо работающими прошивками.
- SPI-режим (Mode 0: CPOL=LOW/CPHA=1EDGE) и логика DC/CS (DC=0 для команды, DC=1 для данных, CS
  дёргается вокруг каждой SPI-транзакции) — совпадают с обоими референсами.
- Используется `HAL_SPI_Transmit()` — H7-специфика SPIv3 (регистры TSIZE/CSTART, которых нет в
  SPI старых серий) обрабатывается HAL автоматически, ручного вмешательства не требует.

### Что пробовали исправить в этой сессии — эффекта не дало

1. **Скорость GPIO на пинах SPI2 (PB13/14/15): `GPIO_SPEED_FREQ_LOW` → `GPIO_SPEED_FREQ_VERY_HIGH`**
   (`Core/Src/stm32h7xx_hal_msp.c`, функция `HAL_SPI_MspInit`). Гипотеза была: на скорости LOW фронты
   SPI на ~6.25 МГц могли "заваливаться" по слю-рейту и контроллер получал искажённые байты команд.
   Правка внесена руками в generated-код (вне `USER CODE` — слетит при регенерации из `.ioc`, для
   постоянства нужно продублировать в CubeMX: Connectivity → SPI2 → GPIO Settings → Maximum output
   speed = Very High для PB13/14/15).
   **Результат: экран остался белым.**
2. **Деселект TP_CS** — в начале `LCD_Init()` добавлен
   `HAL_GPIO_WritePin(TP_CS_GPIO_Port, TP_CS_Pin, GPIO_PIN_SET)`. До этого TP_CS с самого старта
   держался в LOW (задаётся в `MX_GPIO_Init()` как исходный уровень для всей группы пинов GPIOC), то
   есть тач-контроллер XPT2046 был постоянно выбран на одной физической SPI2-шине с экраном.
   **Результат: экран остался белым** (баг сам по себе реальный и полезный для будущей работы тача,
   но не единственная причина белого экрана).

Обе правки применены одновременно, после каждой — пересборка и прошивка через DFU
(см. процедуру выше). Внешне ничего не изменилось: экран как был ровным белым, так и остался.

### Следующий шаг диагностики (пока не проверялся)

Прочитать ID-регистр ILI9486 (команда `0xD3`, ожидаемый ответ `00 94 86`) через `HAL_SPI_TransmitReceive`
(MISO разведён на PB14, physически подключён, используется штатно для тача). Это даст однозначный
ответ на главный вопрос: доходят ли байты до контроллера вообще (проблема в физике/SPI-линке —
пайка, разводка, тайминги) или SPI-линк исправен и дело именно в логике инициализации/адресации
GRAM после неё. Пока этот тест не выполнялся — приоритетный шаг для следующей сессии.

### Обновление (та же сессия, 2026-09-07): проблема воспроизводится на ДВУХ разных проектах/платах

У пользователя есть второй, отдельный проект на другом STM32-борде — тоже с этим же экраном Waveshare,
тоже белый экран, независимо от кода. Это меняет диагноз: раз два разных МК с разной прошивкой дают
одинаковый результат, а Arduino на этом же физическом шилде работает — дело почти наверняка не в
прошивке STM32 (мы её дважды сверяли построчно с официальными рабочими источниками, см. выше), а в
физическом уровне: пайка/разводка/переключатель на самом шилде.

**Нашли на плате шилда физический DIP-переключатель "SPI Config" (3 позиции), подписанный на плате как
`SCLK\D13 MISO\D12 MOSI\D11`.** Сверено с официальным `3.5inch_TFT_Touch_Shield_User_Manual_EN.pdf`
(Waveshare): переключатель выбирает, откуда шилд берёт SPI-сигнал, когда он **механически надет сверху
на плату** (Arduino Uno / Nucleo) — либо с разъёма ICSP (положение по умолчанию), либо с пинов D13/D12/D11
самого шилд-разъёма. У официального Arduino Uno оба положения электрически дают один и тот же сигнал
(ICSP и D11-D13 у Uno и так соединены на самой плате Uno) — поэтому переключатель "ничего не меняет" на
Arduino, это ложное подтверждение, что переключатель ни при чём.

**Проверили: переключили SPI Config в другое положение на обоих проектах, без перепрошивки —
экран остался белым.** Переключатель как минимум для нашей схемы подключения (пайка на отдельную
промаркированную гребёнку сбоку платы: SCLK/MISO/MOSI/LCD_CS/...) эффекта не даёт.

**Рабочая гипотеза на конец сессии:** официальный STM32-пример Waveshare (`XNUCLEO-F103RB`) в этом же
пакете подключается, надевая шилд СВЕРХУ на плату через её родной Arduino-разъём (см. таблицу в PDF:
`STM32 PIN` для XNUCLEO-F103RB — это просто штатная распиновка Arduino-разъёма самой Nucleo-платы,
SCLK=PA5=D13 и т.д.). Наша схема — это пайка проводов на ОТДЕЛЬНУЮ промаркированную гребёнку сбоку
корпуса шилда, а не механическая посадка сверху. Не исключено, что эта боковая гребёнка не является
той же самой цепью, что уходит на сам чип экрана в рабочей конфигурации — то есть возможен обрыв/иная
разводка именно там, куда мы физически подключены проводами.

**Инструмент для следующей проверки:** у пользователя есть цифровой осциллограф Siglent SDS802X HD
(70 МГц, 2 GSa/s, есть функция Decode — предположительно умеет декодировать SPI). Он подходит для
однозначной проверки: физически ли доходит SPI-сигнал (SCLK/MOSI/CS) до пинов на боковой гребёнке при
работающей прошивке, есть ли вообще активность на этих линиях, и соответствует ли она ожидаемым
~6.25 МГц пачкам во время `LCD_Init()`/`LCD_FillScreen()`. Пользователь пока не очень уверенно
пользуется осциллографом — подробный план проверки см. в разделе ниже. Запланировано на вечер
2026-09-07.

## План тестирования осциллографом (Siglent SDS802X HD) — на вечер 2026-09-07

Цель: понять, доходит ли SPI-сигнал физически до пинов боковой гребёнки шилда, куда припаяны провода
на STM32H723VGT6, и если доходит — похож ли он на то, что должно быть (пачки импульсов при передаче,
корректные уровни на CS/RST/BL/DC).

### Подготовка

1. На щупе канала **1** (жёлтый) переключатель ослабления поставить в **x1** (сигнал 3.3В, ослабление
   не нужно, x1 даёт максимальную чувствительность и меньше путаницы для новичка).
2. Крокодил-клемму щупа (GND щупа) — на любой **GND** платы STM32H723VGT6.
3. Кончик щупа — по очереди на пины боковой гребёнки шилда, куда припаяны провода (см. таблицу пинов
   выше): SCLK, MOSI, LCD_CS, LCD_RST, LCD_BL, LCD_DC.
4. Прошивка на плате должна быть запущена и крутить цикл `LCD_FillScreen` (то есть постоянно что-то
   передавать по SPI) — иначе на статичном сигнале ловить нечего.

### Как снять сигнал (по одному пину за раз)

1. Подключить щуп к нужному пину.
2. Нажать синюю кнопку **Auto Setup** (правый верхний угол панели) — осциллограф сам подберёт масштаб
   по напряжению и времени под увиденный сигнал.
3. Посмотреть на экран и зафиксировать результат (см. ниже, что означает каждая картина).
4. Переставить щуп на следующий пин, повторить.

### Что означает увиденное

| Пин | Ожидается (норма) | Если не так |
|---|---|---|
| SCLK | короткие пачки прямоугольных импульсов (~6.25 МГц внутри пачки), повторяются циклично | ровная линия на 0В → сигнал не доходит физически (обрыв/пайка) |
| MOSI | то же самое — пачки импульсов | ровная линия → обрыв |
| LCD_CS | в основном 3.3В (высокий), коротко проваливается в 0В на время каждой передачи | всегда 0В или всегда 3.3В → CS не переключается, обрыв или неверный пин |
| LCD_RST | один раз поднимается в 3.3В и остаётся там (после старта, ~1.5 сек сброс 500/500/500мс) | застрял на 0В → экран физически в сбросе, ничего не заработает независимо от прошивки |
| LCD_BL | ровные 3.3В постоянно | 0В → подсветка не запитана (хотя физически она горит по факту, так что этот пин скорее для контроля) |
| LCD_DC | дёргается между 0В и 3.3В (команда/данные) | ровная линия → DC не переключается |

### Итог проверки

Если на каком-то из пинов (особенно SCLK/MOSI/CS) — ровная линия без активности при работающей
прошивке, это однозначно локализует проблему в физике/пайке именно в этой точке, и дальше можно не
трогать код вообще, а искать обрыв. Если сигналы на всех пинах выглядят нормально — значит физика в
порядке, и надо возвращаться к логике инициализации/адресации GRAM в `lcd_ili9486.c`.

Результат проверки — записать сюда отдельным пунктом после того, как она будет проведена.
