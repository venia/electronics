# GFX-WaveShare: STM32H723VGT6 + Waveshare 3.5" SPI TFT (ILI9486) + TouchGFX

Полная хронология проекта: с нуля в CubeMX, экран в TouchGFX Designer, прошивка через
STM32CubeProgrammer, и разбор всех ошибок/багов по порядку — от "не собирается" до
текущего "белый экран", с шагами аппаратной диагностики осциллографом.

---

## ЧАСТЬ 1. ЖЕЛЕЗО

- **Плата**: STM32H723VGT6 Mini Core Board (WeAct-совместимая, Cortex-M7 550МГц max,
  RAM 564KB, ROM 1024KB), подключена к экрану проводами (не готовый шилд).
- **Экран**: Waveshare 3.5" SPI TFT LCD, 480×320, резистивный тач (контроллер XPT2046),
  драйвер экрана семейства ILI9486, разъём — тот же, что у "Waveshare 3.5inch RPi LCD (A)".

### 1.1 Финальная таблица пинов (SPI2)

| Waveshare (экран) | STM32 (нога) | Назначение |
|---|---|---|
| 5V | 5V платы | питание модуля (обязательно 5V, не 3.3V — подсветка) |
| GND | GND (любой) | земля |
| SCLK | PB13 | SPI2_SCK |
| MISO | PB14 | SPI2_MISO (нужен для тача) |
| MOSI | PB15 | SPI2_MOSI |
| LCD_CS | PC0 | выбор чипа экрана |
| LCD_DC | PC1 | команда/данные |
| LCD_RST | PC2 | сброс экрана |
| LCD_BL | PC3 | подсветка |
| TP_CS | PC4 | выбор чипа тача |
| TP_IRQ | PC5 | прерывание тача (можно не подключать, опрашивать вручную) |

SD-карта и TP_BUSY на модуле есть, но не критичны для старта — не подключены.

## ЧАСТЬ 2. STM32CubeMX — пошагово, как было сделано

### 2.1 Создание проекта
1. `File → New Project → MCU Selector` → ввести `STM32H723VGTx` → выбрать корпус LQFP100 → `Start Project`

### 2.2 Pinout & Configuration — периферия
- **SPI2** → Mode: **Full Duplex Master** (не Transmit Only! — MISO нужен для тача XPT2046)
  - На картинке чипа кликнуть PB13→SPI2_SCK, PB14→SPI2_MISO, PB15→SPI2_MOSI
- **GPIO** (System Core → GPIO), выставить вручную и переименовать (User Label):
  - PC0 → GPIO_Output → **LCD_CS**
  - PC1 → GPIO_Output → **LCD_DC**
  - PC2 (в этом пакете подписан как **PC2_C**) → GPIO_Output → **LCD_RST**
  - PC3 (подписан как **PC3_C**) → GPIO_Output → **LCD_BL**
  - PC4 → GPIO_Output → **TP_CS**
  - PC5 → GPIO_Input → **TP_IRQ**
  - Для всех Output-пинов: Output level = High, Mode = Output Push-Pull, Pull = No pull, Speed = Low
  - ⚠️ PC2_C/PC3_C — на STM32H7 это пины с внутренним аналоговым свичом (общая площадка с
    компаратором/ОУ). CubeMX сам добавляет в `MX_GPIO_Init()` два вызова
    `HAL_SYSCFG_AnalogSwitchConfig(SYSCFG_SWITCH_PC2/PC3, ..._CLOSE)` — без этого GPIO может
    не работать как обычный вывод. Проверено — CubeMX сделал это автоматически, ничего
    руками добавлять не пришлось.
- **CRC** (Computing → CRC) — просто поставить галочку **Activated** (обязательная
  зависимость TouchGFX, без неё генератор ругается "Please Enable CRC IP")

### 2.3 Clock Configuration
- HSI как источник (HSE не разводили) → PLL: M=4, N=25, P=1, Q=2, R=2
- Итог: **SYSCLK = 400МГц**, CPU/Systick = 400МГц, AXI/HCLK3 = 200МГц, APB-шины 100-200МГц
- Отдельно важно: **SPI1,2,3 Clock Mux → PLL1Q = 200МГц** (источник тактирования для SPI2)

### 2.4 Software Packs → X-CUBE-TOUCHGFX
- Mode: галочка **Graphics Application**
- Display:
  - Interface: **Custom**
  - Framebuffer Pixel Format: **RGB565**
  - Width: **480**, Height: **320**
  - **Framebuffer Strategy: "Partial Buffer - GRAM display"** ⚠️ ключевой выбор —
    именно этот вариант (не Single/Double Buffer, не просто "Partial Framebuffer")
    предназначен под дисплеи с собственным GRAM и адресацией через CASET/RASET, как ILI9486
  - Number of Blocks: **3**, Block Size: **2048 bytes**
- Driver:
  - Application Tick Source: **Custom** (см. Часть 4.2 — почему это важно)
  - Use DMA2D Accelerator (ChromART): **No**
  - Real-Time Operating System: **No OS**
- Additional Features: Partial Framebuffer VSync/External Data Reader/Vector Rendering — все Disabled
- Video Decoding: Disabled

### 2.5 Project Manager
- Toolchain/IDE: **STM32CubeIDE**
- **GENERATE CODE**

Что CubeMX реально генерирует этим шагом: `Core/`, `Drivers/`, `Middlewares/ST/touchgfx/*`
(framework, 3rdparty/libjpeg, lib), `TouchGFX/target/generated/*` (glue-код HAL),
`TouchGFX/App/*`, файл-заготовку `TouchGFX/ApplicationTemplate.touchgfx.part`.

⚠️ **Известный баг, с которым уже сталкивались**: один раз CubeMX **пропустил копирование
`Middlewares/ST/touchgfx`** целиком (тысячи файлов фреймворка) — пришлось вручную
скопировать эту папку из соседнего проекта (Project1, та же версия пакета 4.26.1).
Механизм сбоя не выяснен (похоже на нестабильность самого CubeMX/кэша пакетов), но
итоговый воркэраунд — просто взять `Middlewares/ST/touchgfx` из рабочего проекта той же
версии TouchGFX.

## ЧАСТЬ 4. КОД — что дописано руками, и зачем

### 4.1 `Core/Src/main.c` — драйвер ILI9486 (секция `USER CODE BEGIN PV`)

CubeMX сам такой код не генерирует — это ручная реализация протокола ILI9486 поверх
HAL SPI:

```c
#define LCD_CS_LOW()   HAL_GPIO_WritePin(LCD_CS_GPIO_Port, LCD_CS_Pin, GPIO_PIN_RESET)
#define LCD_CS_HIGH()  HAL_GPIO_WritePin(LCD_CS_GPIO_Port, LCD_CS_Pin, GPIO_PIN_SET)
#define LCD_DC_CMD()   HAL_GPIO_WritePin(LCD_DC_GPIO_Port, LCD_DC_Pin, GPIO_PIN_RESET)
#define LCD_DC_DATA()  HAL_GPIO_WritePin(LCD_DC_GPIO_Port, LCD_DC_Pin, GPIO_PIN_SET)

static void LCD_WriteCmd(uint8_t cmd) {
    LCD_DC_CMD();
    LCD_CS_LOW();
    HAL_SPI_Transmit(&hspi2, &cmd, 1, HAL_MAX_DELAY);
    LCD_CS_HIGH();
}

// БЕЗ static — вызывается из C++ (TouchGFXHAL.cpp)
void LCD_WriteData(uint8_t *data, uint16_t len) {
    LCD_DC_DATA();
    LCD_CS_LOW();
    HAL_SPI_Transmit(&hspi2, data, len, HAL_MAX_DELAY);
    LCD_CS_HIGH();
}
```
Логика: DC-пин переключает контроллер между режимом "это команда" (LOW) и "это данные"
(HIGH) — стандартная конвенция для большинства SPI TFT-контроллеров (ILI93xx/94xx серии).
CS обрамляет каждую транзакцию отдельно (bit-banged, не аппаратный NSS — `SPI_NSS_SOFT`
в конфиге SPI2, чтобы самим управлять CS без привязки к таймингам периферии).

```c
static void ILI9486_Init(void) {
    HAL_GPIO_WritePin(LCD_RST_GPIO_Port, LCD_RST_Pin, GPIO_PIN_RESET);
    HAL_Delay(20);
    HAL_GPIO_WritePin(LCD_RST_GPIO_Port, LCD_RST_Pin, GPIO_PIN_SET);
    HAL_Delay(150);

    LCD_WriteCmd(0x01); HAL_Delay(120);   // SWRESET
    LCD_WriteCmd(0x11); HAL_Delay(120);   // Sleep out
    LCD_WriteCmd(0x3A); LCD_WriteData8(0x55); // Pixel format RGB565
    LCD_WriteCmd(0xC0); ... // Power Control 1/2/3, VCOM, Gamma — параметры "по даташиту примера"
    LCD_WriteCmd(0x21);                    // INVON (инверсия цвета для этой матрицы)
    LCD_WriteCmd(0x36); LCD_WriteData8(0x48); // MADCTL — ориентация, НЕ проверена на железе
    LCD_WriteCmd(0x29); HAL_Delay(150);    // Display ON
    HAL_GPIO_WritePin(LCD_BL_GPIO_Port, LCD_BL_Pin, GPIO_PIN_SET); // подсветка, полярность НЕ проверена
}

// БЕЗ static — вызывается из C++
void ILI9486_SetAddrWindow(uint16_t x0, uint16_t y0, uint16_t x1, uint16_t y1) {
    uint8_t buf[4];
    buf[0]=(x0>>8)&0xFF; buf[1]=x0&0xFF; buf[2]=(x1>>8)&0xFF; buf[3]=x1&0xFF;
    LCD_WriteCmd(0x2A); LCD_WriteData(buf,4); // CASET — столбцы
    buf[0]=(y0>>8)&0xFF; buf[1]=y0&0xFF; buf[2]=(y1>>8)&0xFF; buf[3]=y1&0xFF;
    LCD_WriteCmd(0x2B); LCD_WriteData(buf,4); // RASET — строки
    LCD_WriteCmd(0x2C); // RAMWR — после этой команды все последующие data-байты идут в GRAM
}
```
`ILI9486_Init()` вызывается в `main()` один раз, сразу после `MX_TouchGFX_Init()`
(в секции `USER CODE BEGIN 2`).

Пометки в самом коде "проверим на практике" (MADCTL=0x48, полярность подсветки) —
это НЕ подтверждённые значения, взяты как отправная точка из типового примера, реальная
проверка на конкретной матрице ещё не проводилась (см. Часть 6, текущий баг "белый экран"
может быть с этим не связан, но после решения текущей проблемы это первое, что стоит
перепроверить).

### 4.2 `Core/Src/stm32h7xx_it.c` — подключение тика TouchGFX

```c
/* USER CODE BEGIN PFP */
extern void touchgfx_tick(void);
/* USER CODE END PFP */
...
void SysTick_Handler(void)
{
  HAL_IncTick();
  /* USER CODE BEGIN SysTick_IRQn 1 */
  touchgfx_tick();
  /* USER CODE END SysTick_IRQn 1 */
}
```
**Зачем**: в CubeMX выбрано `Application Tick Source = Custom` — это значит framework
TouchGFX **не получает** автоматический источник кадровых тиков (в отличие от плат
с LTDC, где это делает VSYNC-прерывание контроллера). Без ручного вызова источника
тиков framework вообще не запускает цикл рендеринга — экран просто никогда не
обновляется (в прошлом проекте на маленьком экране именно это давало эффект
"шума"/"снега" на дисплее). Здесь этот фикс **был перенесён заранее**, ещё до первого
запуска — правильно сделано.

### 4.3 `TouchGFX/target/TouchGFXHAL.cpp` — связка framework ↔ SPI-драйвер

```cpp
extern "C" void touchgfx_tick(void)
{
    HAL::getInstance()->vSync();       // счётчик кадров framework (не обязателен, но "по документации")
    OSWrappers::signalVSync();          // САМАЯ важная строка — говорит framework "пора рисовать кадр"
}
```

Дальше — реализация хуков, обязательных именно для стратегии
**"Partial Buffer - GRAM display"**:

```cpp
namespace touchgfx { void startNewTransfer(); } // форвард-декларация (функция определена в generated-файле)

extern "C" int touchgfxDisplayDriverTransmitActive()
{
    return 0; // HAL_SPI_Transmit блокирующий -> к моменту возврата передача уже завершена
}

extern "C" void touchgfxDisplayDriverTransmitBlock(const uint8_t* pixels, uint16_t x, uint16_t y, uint16_t w, uint16_t h)
{
    ILI9486_SetAddrWindow(x, y, x + w - 1, y + h - 1);

    const uint16_t* src = (const uint16_t*)pixels;
    static uint8_t lineBuf[480 * 2];
    for (int row = 0; row < h; row++)
    {
        for (int col = 0; col < w; col++)
        {
            uint16_t px = src[row * w + col];
            lineBuf[col * 2]     = (uint8_t)(px >> 8);   // RGB565 -> старший байт первым (SPI MSB-first)
            lineBuf[col * 2 + 1] = (uint8_t)(px & 0xFF);
        }
        LCD_WriteData(lineBuf, w * 2);
    }

    startNewTransfer(); // сообщаем аллокатору "блок отправлен, можно брать следующий"
}
```

**Зачем именно так**: при "Partial Buffer" framework сам рисует изменившиеся виджеты в
маленькие блоки (`ManyBlockAllocator<2048, 3, 2>` — 3 блока по 2048 байт = 1024 пикселя
каждый, см. `TouchGFXGeneratedHAL.cpp`), и когда блок готов — сам вызывает
`touchgfxDisplayDriverTransmitBlock(pixels, x, y, w, h)` с готовым указателем на пиксели
именно этого блока и его координатами на экране. Наша задача — просто отправить их по
SPI (с перестановкой байт под RGB565/MSB-first) и вызвать `startNewTransfer()`, чтобы
framework увидел "передача завершена, дай следующий блок, если есть".

```cpp
void TouchGFXHAL::flushFrameBuffer(const touchgfx::Rect& rect)
{
    TouchGFXGeneratedHAL::flushFrameBuffer(rect);
}
```
Просто прокси к generated-версии — именно она внутри себя дергает
`frameBufferAllocator->markBlockReadyForTransfer()` и первый вызов
`touchgfxDisplayDriverTransmitBlock`.

## ЧАСТЬ 5. STM32CubeProgrammer — прошивка через DFU (USB)

Отдельного программатора (ST-Link) не использовали — только встроенный USB DFU-бутлоадер.

1. **Перевод платы в DFU**: зажать **BOOT0**, не отпуская — тапнуть **RESET/NRST**,
   подождать ~0.5 сек, отпустить **BOOT0**. Плата виснет в USB DFU-режиме (обычный код
   не выполняется).
2. **STM32CubeProgrammer**: Interface = **USB** → **Refresh** (должно появиться
   "STM32 BOOTLOADER" устройство) → **Connect**
3. Вкладка **Erasing & Programming** → **Browse** → указать файл прошивки.
   - В этом проекте CubeIDE не настроен генерировать `.bin` (нет шага objcopy в
     Build Steps) — прошивали напрямую **`Debug/GFX-WaveShare.elf`**.
     CubeProgrammer прошивает `.elf` так же нормально, как `.bin`/`.hex`, и сам берёт
     адрес старта из файла — вручную вбивать `0x08000000` не нужно (это актуально
     только для чистого `.bin`)
4. Обязательно галочка **"Run after programming"** — без неё плата останется висеть в
   DFU после записи (будет казаться, что "ничего не изменилось", хотя прошивка прошла)
5. **Start Programming**

## ЧАСТЬ 6. ХРОНОЛОГИЯ ОШИБОК И ТЕКУЩЕЕ СОСТОЯНИЕ

### 6.1 Ошибка сборки №1 — `fatal error: gui/common/FrontendHeap.hpp: No such file or directory`

**Причина**: `TouchGFX/generated/` и `TouchGFX/gui/` физически не существовали.
CubeMX Generate Code создаёт только glue-код и заготовку, а сам GUI-код (экраны,
шрифты, тексты, `FrontendHeap.hpp`) генерирует **TouchGFX Designer** отдельным шагом
(`Code → Generate Code` в самом Designer, см. Часть 3, шаг 4) — этот шаг ни разу не
выполнялся до этого момента (кнопки Play/`</>` внизу канваса Designer, которые
нажимались, относятся к симулятору/предпросмотру и не создают код для целевой платы).

**Решение**: выполнить `Code → Generate Code` в TouchGFX Designer. После этого
появились `TouchGFX/generated/`, `TouchGFX/gui/`, `TouchGFX/simulator/`,
`TouchGFX/config/`, `TouchGFX/target.config` — компиляция (не линковка) прошла успешно.

### 6.2 Ошибка линковки №2 — сразу после фикса №1

```
undefined reference to `TouchGFXGeneratedHAL::advanceFrameBufferToRect(...)`
undefined reference to `touchgfxDisplayDriverTransmitActive'
undefined reference to `touchgfxDisplayDriverTransmitBlock'
```

**Причины (две независимые)**:
1. `TouchGFXHAL::flushFrameBuffer()` изначально был написан по образцу **Single Buffer**
   стратегии (копия логики из прошлого проекта на маленьком экране) — вызывал
   `getTFTFrameBuffer()`, а generated-код при **Partial Buffer - GRAM display**
   стратегии эта функция всегда возвращает `0` (`// getTFTFrameBuffer() not used for
   selected Frame Buffer Strategy`). Плюс сама `advanceFrameBufferToRect` объявлена
   `inline`, но нигде не используется внутри своего же `.cpp` — компилятор просто не
   генерирует для неё внешний символ, и линковка из другого файла падает.
2. `touchgfxDisplayDriverTransmitActive()`/`touchgfxDisplayDriverTransmitBlock()` —
   обязательные хуки именно для Partial Framebuffer-стратегии (framework их реально
   вызывает, см. `TouchGFXGeneratedHAL.cpp`), но никто их не реализовал — только
   `#warning`-подсказки в generated-шаблоне об этом и говорили.

**Решение**: переписан `TouchGFX/target/TouchGFXHAL.cpp` — `flushFrameBuffer` теперь
просто прокси к generated-версии, а `touchgfxDisplayDriverTransmitActive/Block`
реализованы через уже существующие `ILI9486_SetAddrWindow`/`LCD_WriteData` (см. Часть 4.3).
После этого — **сборка и линковка полностью прошли успешно**.

### 6.3 Прошивка — успешно

DFU-прошивка (Часть 5) прошла без проблем, плата запускается.

### 6.4 Текущий баг — экран сплошной белый (в процессе диагностики)

**Симптом**: после прошивки подсветка включается, но весь экран равномерно белый —
не чёрный, не "снег"/шум, а именно ровный белый цвет, не реагирующий ни на что.

**Уже исключено:**
- ✅ TouchGFX-уровень — временно вставлена **прямая заливка экрана в обход framework**
  (`ILI9486_SetAddrWindow` + `LCD_WriteData` напрямую в `main()`, минуя TouchGFX
  полностью) — экран всё равно остаётся белым → проблема НЕ в связке с TouchGFX,
  а ниже, на уровне SPI/ILI9486-протокола или физики.
- ✅ Скорость SPI — было `SPI_BAUDRATEPRESCALER_8` (25МГц из 200МГц источника),
  снижено до `SPI_BAUDRATEPRESCALER_64` (~3.125МГц) — белый экран остался тем же,
  скорость не является причиной.
  ⚠️ Это изменение сделано прямо в `MX_SPI2_Init()` в `main.c`, **вне блоков
  `USER CODE`** — при следующей генерации кода из CubeMX оно слетит. Если скорость
  окажется важна для финального решения — обязательно продублировать в самом CubeMX
  (Pinout & Configuration → SPI2 → Baud Rate Prescaler).
- ✅ Пайка/непрерывность проводов — мультиметром (прозвонка, питание выключено)
  проверены SCLK/MOSI/CS/DC/GND между платой и экраном — везде норма.

**это временный диагностический код, не финальная логика**, TouchGFX/`while(1)` с

контроллер экрана держится в аппаратном сбросе и игнорирует весь (полностью корректный!)
SPI-трафик — это объяснило бы симптом "белый экран всегда, что бы ни слали". После RST

**RST (PC2) — проверено осциллографом:** при нажатии физического RESET на плате STM32
уровень на линии проседает как положено → ✅ работает корректно.

уровня → ✅ работает корректно.

**Итог по всем 5 сигналам: CS, SCLK, MOSI, RST, DC — все подтверждены осциллографом
как электрически корректные.** МК гарантированно передаёт правильно оформленный
SPI-протокол. Экран при этом остаётся ровным белым — то есть проблема не в проводке
и не в тайминге сигналов.

### 6.5 Уточнение модели экрана

По фото задней стороны платы экрана выяснилось: это **не** "Waveshare 3.5inch RPi LCD (A)"
(HAT для Raspberry Pi), а **"Waveshare 3.5inch TFT Touch Shield"** — версия для Arduino,
320×480, XPT2046 touch, контроллер **ILI9486** (подтверждено официальной вики Waveshare).
На плате есть блок **"SPI Config"** — DIP-переключатель `SCLK\D13, MISO\D12, MOSI\D11`,
выбирающий, куда внутри платы подключены линии SPI (на выделенные пины заголовка или на
D13/D12/D11 под Arduino Uno).

**Проверено — переключатель SPI Config в обоих положениях** → результат не изменился,
экран всё равно белый. Значит переключатель не является причиной (либо не влияет на
используемые нами пины вообще).

### 6.6 Сверка инициализации с рабочим эталоном

Нашли подтверждённо рабочую библиотеку именно под эту матрицу:
`ImpulseAdventure/Arduino-TFT-Library-ILI9486` на GitHub (сделана под "3.5 inch RPi LCD (A)
320x480 from Waveshare" — та же панель). Сравнили построчно с нашим `ILI9486_Init()`,
нашли и исправили расхождения:
- Убраны лишние команды **0xC0 (Power Control 1)** и **0xC1 (Power Control 2)** —
  в рабочем эталоне их нет вообще
- **0xC2 (Power Control 3)**: было `0x55`, исправлено на `0x44` (как в эталоне)
- Инверсия дисплея: было `0x21` (INVON), исправлено на `0x20` (INVOFF — вариант "(A)")
- Пиксель-формат (0x3A=0x55), гамма (0xE0/0xE1), MADCTL(0x36=0x48) уже совпадали

**Результат после этого фикса — экран остался белым, без изменений.**

### 6.7 Гипотеза "не та ориентация/адресация" — проверено, не подтвердилось

Предположение: TouchGFX/CubeMX настроены на альбомные 480×320, а MADCTL=0x48
(скопированный из эталона) не включает бит **MV** (row/column exchange, бит 5) —
то есть остаётся портретная адресация панели (родной GRAM ILI9486 — 320×480), а мы
шлём CASET/RASET исходя из альбомных координат (0-479 по X), что может уходить в
невалидную область адресации.

**Проверено**: MADCTL изменён с `0x48` на `0x68` (добавлен бит MV) — **экран всё равно
остался полностью белым, без единого изменения**. Гипотеза не подтвердилась (или MV —
не единственное, что нужно было поменять; MX/MY тоже не переподбирались после этого).

### 6.8 Текущий статус — на чём остановились

Все проверенные и **исключённые** причины:
- ❌ Связка с TouchGFX (прямая заливка в обход framework — тот же результат)
- ❌ Скорость SPI (25МГц и 3.125МГц — без разницы)
- ❌ Пайка/непрерывность проводов (CS/SCLK/MOSI/DC/GND — мультиметром чисто)
- ❌ Электрическая корректность CS/SCLK/MOSI/RST/DC (все 5 подтверждены осциллографом)
- ❌ Положение переключателя SPI Config (оба положения — без разницы)
- ❌ Параметры инициализации Power Control/VCOM/Inversion (исправлены на подтверждённо
  рабочие значения из эталонной библиотеки — без разницы)
- ❌ Бит MV в MADCTL (добавлен — без разницы)

**Ещё не проверено — кандидаты на следующую сессию:**
1. **Реальное напряжение 5V под нагрузкой** (не прозвонка, а мультиметр в режиме
   измерения напряжения, во время работы платы) — возможно, 5V проседает и панели не
   хватает питания для внутренних DC-DC/заряд-насосов, генерирующих VGH/VGL/GVDD —
   это дало бы ровно такой симптом (панель физически не может модулировать свет,
   светится "по умолчанию" = белый), независимо от абсолютно корректного SPI
2. **Подсветка (LCD_BL)** — то, что она "визуально горит", не проверено осциллографом/
   логически как факт переключения по нашему GPIO — возможно, подсветка на модуле вообще
   не управляется этим пином (запитана напрямую, всегда горит) — тогда "подсветка
   работает" ничего не подтверждает, и полярность/логика BL не проверена по-настоящему
3. **Разные MX/MY биты MADCTL** — пробовали только добавление MV, но не перебирали
   остальные комбинации (0x28, 0x88, 0xE8 и т.д.) — раз MV не помог, возможно дело не в
   ориентации вообще, и дальше копать MADCTL уже низкий приоритет
4. Возможно стоит попробовать **записать в GRAM не через RAMWR полный кадр, а прочитать
   Read Display Power Mode (0x0A) или Read Display Status (0x09)** через MISO — раз SPI2
   настроен Full Duplex, можно реально прочитать регистр состояния с контроллера и
   получить железное доказательство, что чип вообще отвечает на команды (а не просто
   молча их принимает) — это развяжет "чип получает команды, но физически не может
   отобразить" от "чип в принципе не отвечает/не тот чип/не то питание"
5. Проверить не спутан ли сам модуль — есть шанс, что это клон с другим (несовместимым)
   вариантом ILI9486 или с дефектом самой платы (заводской брак) — стоит поискать
   даташит/маркировку конкретной SPI-микросхемы на плате рядом с шлейфом экрана

### 6.9 Чтение регистров состояния через MISO — попробовано, результат неубедительный/тупиковый

Реализован был кандидат №4 (функция `LCD_ReadReg`, чтение `0x0A` Power Mode и `0x04`
Display ID). **Осциллографом (Siglent SDS802X HD) сняты 2 скриншота MISO (PB14):**
- 1мкс/дел: линия плоская, ~3.27В, шум ~19мВ — уровень покоя, никакого переключения.
- 100мкс/дел (то самое "раз в секунду становится чуть толще" по описанию пользователя):
  среднее ~3.37В, редкие всплески ~230кГц, размах всего ~300мВ.

**Вывод: это не похоже на настоящий цифровой ответ чипа.** При реальном ответе по SPI
MISO обязан был бы дать чёткий меандр полным размахом (0↔3.3В) на частоте SCLK
(3.125МГц) — как и подтверждённый ранее MOSI. Наблюдаемая картина (маленький размах,
частота на порядок ниже SCLK) больше похожа на наводку/просачивание от соседних линий
(CS/MOSI), а не на данные.

**Важная оговорка, обесценивающая сам тест**: это Waveshare-шилд для Arduino
(4-wire SPI). У многих таких бюджетных модулей вывод данных самого LCD-контроллера
(SDO) **вообще не разведён на разъём** — на общую линию MISO выведен только сигнал
тач-контроллера XPT2046, у самой матрицы обратной связи физически нет. Если это тот
случай — плоская линия ничего не доказывает ни за, ни против "чип жив/мёртв", читать
LCD через SPI на этой плате может быть в принципе невозможно.

**Код чтения регистров удалён из `main.c`** (LCD_ReadReg и связанные глобалы) — тест
признан тупиковым, не тратим время дальше в эту сторону.

### 6.10 Новый визуальный тест — Display OFF/ON + инверсия (код добавлен, ждём результата)

Вместо осциллографа — тест, который пользователь может провести просто глядя на экран,
без всякого оборудования. В диагностическом `while(1)` (`main.c`, после заливки
красный/синий, HAL_Delay 2000мс между шагами) добавлена последовательность команд:

1. `0x28` Display OFF — экран должен потухнуть/помутнеть
2. `0x29` Display ON — должен вернуться прежний вид
3. `0x21` Inversion ON — цвета должны инвертироваться
4. `0x20` Inversion OFF — должно вернуться обратно

**Как трактовать результат:**
- Если хоть один шаг визуально меняет картинку (гаснет/тускнеет на OFF, меняется
  оттенок на инверсии) → контроллер реально что-то делает с пикселями, GRAM/протокол
  в целом работают, проблема более тонкая (конкретно в данных кадра/адресации/самой
  матрице).
- Если экран остаётся ровно белым **на всех четырёх состояниях без единого изменения**
  → сильный аргумент за кандидат #1 из журнала (внутренние напряжения смещения панели
  VGH/VGL/GVDD не генерируются/не хватает — чип физически не может модулировать свет,
  что бы ему ни слали). В этом случае следующий шаг — маловероятно что software-фикс,
  переходить к прямой проверке реального 5В под нагрузкой мультиметром (кандидат #1)
  и/или проверке модуля на брак/несовместимость (кандидат #5).

**РЕЗУЛЬТАТ (проверено на железе): экран НЕ меняется вообще, ни на одном из 4 шагов.**
Ни Display OFF, ни Display ON, ни обе инверсии — визуально неотличимы, экран остаётся
ровно белым. Это уже третий независимый тест подряд, где никакое изменение команд/данных
не даёт вообще никакого визуального эффекта (после: (1) заливка красный/синий — эффекта
нет, (2) чтение регистров через MISO — похоже на наводку, не на ответ чипа, (3) теперь
Display OFF/ON/Inversion — тоже без эффекта). Это сильно смещает подозрение с
протокола/кода на **питание/физику самой матрицы** (кандидат #1) — если бы дело было в
неверной адресации GRAM или формате пикселей, инверсия и Display OFF (которые не зависят
от адресации, а глобально маскируют/инвертируют весь GRAM) почти наверняка дали бы хоть
какой-то видимый эффект.

**Отдельно: получен совет от условного "Google AI" с теорией про сдвиговые регистры
и 16-битный параллельный режим на плате Waveshare, якобы требующий держать CS низким
всю передачу кадра и слать данные 16-битными парами.** Теория отклонена как
маловероятная/ложная — она противоречит уже собранным в этом журнале фактам:
- Раздел 6.4: на MOSI уже виден байтовый паттерн `0xF8/0x00` **один в один, как в коде**
  — если бы на плате стоял сдвиговый регистр, переформатирующий посылки в 16 бит,
  это было бы видно на трассе как другая структура данных, а не прямое повторение
  байтов из прошивки.
- Раздел 6.4: CS/SCLK уже подтверждены как "идеально совпадает с ожидаемым по коду
  поведением", фронты чистые, без звона — значит, ни "срез такта при подъёме CS",
  ни "звон от Very High GPIO Speed" не имеют места на практике.
Модуль Waveshare 3.5" SPI (ILI9486, 4-wire SPI) — обычная плата с прямым SPI-подключением
к контроллеру, без микросхем-регистров. Решено не реализовывать эти советы (держать
CS всю передачу кадра, 16-битные пары) — единственное рациональное зерно в том ответе —
совет проверить подсветку явным переключением GPIO_PIN_RESET, что и так уже было
кандидатом #2 в этом журнале.

### 6.11 Тест подсветки (код добавлен, ждём результата)

В тот же диагностический `while(1)` после теста Display OFF/ON/Inversion добавлено:
`LCD_BL` → `GPIO_PIN_RESET` (должна погаснуть) на 1 секунду → обратно `GPIO_PIN_SET`
(должна загореться) на 1 секунду, циклически. Кандидат #2 из журнала — до сих пор не
проверялся, был только визуально "вроде горит", без подтверждения что это именно наш
GPIO её включает.

**Как трактовать:**
- Если подсветка реально гаснет/загорается синхронно с кодом → PC3 управляет ею
  правильно, полярность верна, кандидат #2 закрыт.
- Если подсветка не реагирует (продолжает гореть или не горит вовсе независимо от
  GPIO) → она либо запитана на модуле напрямую (не через наш пин), либо полярность
  инвертирована — тогда стоит поискать перемычку/резистор на плате экрана рядом с
  выводом BL/LED.

**Следующий приоритетный шаг после этого теста (не требует пайки/осциллографа)**:
мультиметром в режиме измерения напряжения (не прозвонка) измерить реальное 5В под
нагрузкой прямо на выводах экрана, пока плата работает — кандидат #1, наиболее
вероятная причина после трёх подряд "нулевых" тестов выше.

**РЕЗУЛЬТАТ (проверено на железе, важное открытие):** при питании от USB компьютера
подсветка на тест вообще не реагировала. Пользователь **вынул кабель из компьютера и
подключил плату к обычной сетевой зарядке 5В/2.1А** — и подсветка начала **чётко мигать**:
каждые ~13-14 секунд экран на ~1 секунду темнеет. Это ровно совпадает с расчётным
периодом диагностического цикла в коде (5×2000мс + 2×1000мс + время заливки ≈ 13с) —
то есть это буквально наш собственный тест `LCD_BL RESET/SET`, который наконец-то
заработал.

**Вывод по кандидату #2: ЗАКРЫТ.** PC3 действительно управляет подсветкой правильно,
полярность верна — просто питания от компьютерного USB-порта не хватало (типичное
ограничение ~500мА на порт компьютера), а от зарядки 2.1А хватает.

**НО: кандидат #1 ("не хватает 5В для VGH/VGL") этим НЕ подтверждается полностью.**
Пользователь подтвердил: при этой же зарядке 2.1А, кроме гашения подсветки, экран
**всё так же ровно белый** — ни цвет заливки (красный/синий), ни Display OFF, ни
инверсия по-прежнему не дают вообще никакого видимого эффекта. Если бы всё дело было
только в нехватке тока для внутренних зарядных насосов панели, с 2.1А стоило бы
ожидать хоть какого-то сдвига — а сдвига нет вообще никакого, кроме уже объяснённой
подсветки.

**Текущий вывод**: питания МК точно достаточно (цикл идёт ровно по расчётному времени,
GPIO переключается) — то есть прошивка гарантированно исполняется как задумано и
SPI-команды гарантированно уходят. При этом сама матрица не реагирует НИ на один из
трёх принципиально разных типов воздействия (данные пикселей / Display OFF / инверсия).
Это сдвигает главное подозрение с "не хватает питания панели" в сторону **кандидата #5
— сам чип/панель экрана неисправны, несовместимы или бракованы** (или: остался
какой-то до сих пор не пойманный протокольный нюанс конкретно этой платы, не видимый
на осциллографе).

**Следующие шаги (по приоритету)**:
1. Измерить мультиметром (вольтметр, не прозвонка) реальное напряжение **прямо на
   выводах 5V/GND платы экрана** (не на STM32-плате) пока всё работает от зарядки
   2.1А — исключить просадку именно в проводе к экрану (тонкий провод/плохой контакт),
   а не в самом источнике питания.
2. Осмотреть плату экрана на предмет маркировки конкретной микросхемы-контроллера
   рядом со шлейфом матрицы (кандидат #5) — сверить с ожидаемой ILI9486.

### 6.12 ПРОРЫВ — на плате реально есть сдвиговые регистры (74HC4094), протокол переписан

Пользователь рассмотрел плату экрана под увеличительным стеклом и прочитал маркировку
микросхем: **4× 74HC4094**, AMS1117 (стабилизатор питания), XPT2046 (тач), и ещё
одна с маркировкой "YBKBF V125" (не идентифицирована, вероятно сам ILI9486 в
COB-исполнении или его ребрендинг).

**74HC4094 — это ДЕЙСТВИТЕЛЬНО сдвиговые регистры** (8-bit shift-and-store register
с 3-state выходами). Это значит, что примерно за час до этого "Google AI" был прав
в главном тезисе (сдвиговые регистры на плате есть), хотя конкретные технические
детали в его ответе (срез такта при CS, необходимость держать CS всю переда_у кадра,
"16-битные пары" без объяснения зачем) были признаны недостаточно обоснованными на
тот момент — но общее направление оказалось верным.

**Найден и прочитан построчно исходник библиотеки, написанной именно под эту плату**:
[ImpulseAdventure/Waveshare_ILI9486](https://github.com/ImpulseAdventure/Waveshare_ILI9486)
("Arduino library for Waveshare ILI9486 supporting the Waveshare 3.5" & 4" TFT Touch
Shields") — это НЕ та же библиотека, что сверялась в п. 6.6 (та была
`Arduino-TFT-Library-ILI9486`, под "RPi LCD (A)", предположительно обычный 4-wire
SPI без сдвиговых регистров). Комментарий в самом исходнике прямым текстом:

> "Data sheet says min clock width is 66ns... **Except, this thing isn't *actually*
> SPI! It's a 16 bit shift register connected to the parallel interface**"

**Главная находка — формат записи байта:**
```cpp
inline void lcdWriteReg(uint8_t reg) {
    digitalWrite(LCD_DC, LOW);
    SPI.transfer(0);      // ОБЯЗАТЕЛЬНЫЙ нулевой байт-заглушка
    SPI.transfer(reg);    // сам байт
}
```
Каждый логический байт команды/параметра нужно посылать как **2 физических байта**:
`0x00` (старший, чипом не используется) + реальное значение (младший) — потому что
сдвиговый регистр физически 16-битный, и меньшим числом бит корректно не защёлкивается.
**Это, весьма вероятно, и есть причина "белого экрана" всё это время** — ВСЕ наши
команды (Sleep Out, Power Control, Gamma, MADCTL, Display ON/OFF, Inversion — вообще
всё) отправлялись как одиночные 8-битные SPI-transfer'ы, то есть неполными словами,
и матрица их либо не защёлкивала вообще, либо защёлкивала мусор — что идеально
объясняет, почему буквально ничего и никогда не работало.

**Второе важное отличие**: в этой библиотеке CS не дёргается на каждый байт — он
опускается один раз в начале целой операции (`startWrite()`) и поднимается один раз
в конце (`endWrite()`), при этом весь `initializeLcd()` (десятки регистров) идёт под
одним CS, и весь `writeFillRect2()` (адресное окно + все пиксели) — тоже под одним CS.

**Пиксельные данные (RAMWR) дополнительным нулём НЕ дополняются** — RGB565-цвет уже
честные 16 бит, `SPI.transfer16(color)` шлёт их напрямую. Дополнение нулём нужно
только для 8-битных по смыслу значений (регистры, однобайтные параметры,
байты адресного окна CASET/RASET).

**Внесённые изменения в код**:
- `Core/Src/main.c`: переписаны `LCD_WriteCmd`/добавлены `LCD_Cmd`/`LCD_Param`/
  `LCD_WriteCmdParams`/`LCD_Begin`/`LCD_End` — теперь каждый регистр/параметр шлётся
  как `{0x00, значение}`, CS держится низким на всю операцию (команда+параметры,
  или адресное окно+пиксели), а не по байтам.
- `ILI9486_Init()` переписан на регистры и значения из `Waveshare_ILI9486.cpp`
  (`initializeLcd()`) — это теперь основной эталон вместо прежнего "RPi LCD (A)".
  MADCTL взят как `0x68` (соответствует `setRotation(1)` в этой библиотеке — альбомная
  ориентация 480×320, совпадает с нашей уже выбранной гипотезой).
- `ILI9486_SetAddrWindow()` переписан — CASET/RASET теперь тоже с нулевым дополнением,
  функция больше не открывает/закрывает CS сама (это делает вызывающий код через
  `LCD_Begin()`/`LCD_End()`), чтобы адресное окно и последующие пиксели шли одной
  транзакцией.
- `TouchGFX/target/TouchGFXHAL.cpp`: `touchgfxDisplayDriverTransmitBlock()` обновлён
  под тот же принцип — оборачивает `ILI9486_SetAddrWindow()`+цикл `LCD_WriteData()`
  в `LCD_Begin()`/`LCD_End()`. Этот путь пока не используется (диагностический
  `while(1)` в `main.c` в TouchGFX не уходит), но чтобы не оставлять код в заведомо
  несогласованном состоянии, поправлен сразу.

**Статус: изменения внесены, НЕ ПРОВЕРЕНЫ на железе.** Следующий шаг — прошить и
посмотреть, наконец, появится ли реакция экрана (цвет заливки, Display OFF,
инверсия) — впервые с начала всей диагностики есть конкретная, найденная в
первоисточнике причина, а не догадка.

**РЕЗУЛЬТАТ: экран остался ровно белым, без единого изменения.** 16-битное
исправление (0x00 + значение) не дало никакого эффекта — ни заливка, ни Display
OFF/ON, ни инверсия.

### 6.13 Второй совет от "Google AI" — отклонён с обоснованием

**Важно: вывод раздела 6.15 ("панель бракована") оказался НЕВЕРНЫМ.** На основании

стороннего непроверенного источника, а не официального демо-кода производителя —
это была ошибка модели: имея открытый доступ в интернет, надо было сразу зайти на
официальную вики-страницу экрана (со страницы товара есть прямая ссылка WiKi:
https://www.waveshare.com/wiki/3.5inch_TFT_Touch_Shield → архив
`3.5inch_TFT_Touch_Shield_Code_V2.7z`) и взять оттуда официальные примеры, вместо
того чтобы писать собственную реализацию по мотивам чужого GitHub-репозитория.

**Проверка на реальном железе официальными примерами** (распаковано в
`D:\PROJECTS\electronics\STM32\3.5inch_TFT_Touch_Shield_Code_V2\3.5inch_TFT_Touch_Shield_Code`):

Это железно доказывает: **панель и тач-контроллер полностью исправны**, дело было
исключительно в софте/протоколе.

**Найдена настоящая причина белого экрана** — сравнение построчно с официальным
`LCD_Driver.c` (идентичен в Arduino- и в STM32 HAL-версии из пакета, обе публикует
сам производитель, STM32-версия лежит в
`STM32\XNUCLEO-F103RB\lcd3in5-demo\User\LCD\LCD_Driver.c` и `User\Config\DEV_Config.c`).
Протокол оказался **асимметричным**, чего не учла версия из 6.12:

```c
void LCD_WriteReg(uint8_t Reg) {      // КОМАНДА — ровно 1 байт, БЕЗ нулевой заглушки
    LCD_DC_0; LCD_CS_0;
    SPI4W_Write_Byte(Reg);
    LCD_CS_1;
}
void LCD_WriteData(uint8_t Data) {    // ПАРАМЕТР/ДАННЫЕ — Data объявлен uint8_t,
    LCD_DC_1; LCD_CS_0;               // поэтому (Data>>8) всегда 0x00 — параметр
    SPI4W_Write_Byte(Data >> 8);      // реально уходит как 2 байта: 0x00 + значение
    SPI4W_Write_Byte(Data & 0XFF);
    LCD_CS_1;
}
```

Направление гипотезы про сдвиговые регистры 74HC4094 из 6.12 было верным (нулевая
заглушка на параметрах правда нужна), но реализация в 6.12 ошибочно дополняла нулём
**и саму команду тоже** (сначала +1 байт, потом в 6.14 — эксперимент с +3 байтами
"32-битного слова") — это ломало КАЖДУЮ команду целиком, поэтому ни одна из них
не могла подействовать и матрица не реагировала вообще ни на что, что мы наблюдали
во всех тестах 6.4–6.14.

**Дополнительно уточнена ориентация**: официальное демо трактует эту панель как
landscape 480×320 "из коробки", со сканом по умолчанию `D2U_L2R`
(`SCAN_DIR_DFT` в `LCD_Driver.h`) → `MADCTL(0x36) = 0x28`, `0xB6` (Display Function
Control) второй байт данных = `0x62`. Раньше пробовали `0x48`/`0x68` — оба неверны
для этой платы.

**Исправлено в `Core/Src/main.c`**:
- `LCD_Cmd()` — теперь ровно 1 байт (`HAL_SPI_Transmit(&hspi2, &cmd, 1, ...)`), без
  какой-либо нулевой заглушки.
- `LCD_Param()` — теперь ровно 2 байта (`{0x00, val}`), было 4 байта.
- `ILI9486_Init()` — переписан дословным переводом официального `LCD_InitReg()` +
  `LCD_SetGramScanWay(D2U_L2R)` (регистры `0xF9,0xC0,0xC1,0xC2,0xC5,0xB1,0xB4,0xB6,
  0xB7,0xE0,0xE1,0xF1,0xF2,0xF4,0xF8,0x3A`, затем `0xB6`/`0x36` под скан-направление,
  Sleep Out, Display ON), вместо прежнего набора из стороннего ImpulseAdventure-драйвера.
- Тайминги сброса LCD_RST — `SET/500мс → RESET/500мс → SET/500мс`, как в официальном
  `LCD_Reset()` (было 20/150мс).
- `ILI9486_SetAddrWindow()` не менялась структурно (CASET/RASET уже били байт-за-байтом
  через `LCD_Param`, что теперь автоматически стало корректным 2-байтным форматом).

**Статус: исправление внесено в код, ЕЩЁ НЕ ПРОВЕРЕНО на STM32-железе** (сам экран
на момент фикса физически недоступен — был возвращён продавцу на основании неверного
вывода 6.15). Следующий шаг, когда экран снова окажется в руках (тот же самый после
объяснения магазину, что он рабочий, или замена) — прошить STM32 с этим исправлением
и повторить визуальный тест (заливка/Display OFF/инверсия) из 6.10, теперь ожидая
реальной реакции экрана.

**Отдельно — официальный STM32-пример на HAL уже существует и может использоваться

(Keil MDK-ARM проект, STM32F103RB/Nucleo, не STM32H723 и не CubeIDE — портировать
пины/периферию под нашу плату придётся вручную, но сама логика `LCD_Driver.c`
идентична только что описанной и уже перенесена в наш `main.c`).

### 6.17 Прошито с фиксом 6.16 — тот же белый экран, найдена ВТОРАЯ ошибка (CS-семантика)

Пользователь скомпилировал и прошил фикс из 6.16 (билд 0 ошибок/0 предупреждений,
`Core/Src/main.c` реально пересобрался — видно в логе). Результат: **экран всё ещё
ровно белый**, экран темнеет каждые ~13 секунд. Темнение каждые ~13с — это НЕ баг,
это наш же диагностический тест подсветки в конце цикла (2+2+2+2+2+1+1с ≈ расчётные
13с) — то есть прошивка гарантированно новая и реально выполняется, просто картинка
по-прежнему не появляется.

**Найдена вторая, отдельная ошибка** — сравнение официального `LCD_WriteReg`/
`LCD_WriteData`/`LCD_SetWindow` показало: **CS пульсирует на КАЖДУЮ отдельную
запись** (каждый регистр, каждый отдельный байт-параметр — свой независимый
опустить/поднять CS), а НЕ держится низким на всю "логическую" операцию
(регистр+все параметры, или CASET+RASET+RAMWR), как было сделано в 6.12 и
сохранено в фиксе 6.16. Единственное исключение, где CS официально держится
низким дольше одного байта — сам burst пикселей (`LCD_Write_AllData`), и то
только ПОСЛЕ того как RAMWR (0x2C) уже отправлен своим отдельным импульсом CS.

Гипотеза: раз на плате реальные сдвиговые регистры 74HC4094, CS там, похоже,
работает не как классический SPI chip-select, а как строб защёлки — данные
только сдвигаются, пока CS низкий, и физически фиксируются на выходе только
по фронту CS (высокий→низкий или низкий→высокий). Если держать CS низким
на несколько байт-групп подряд (как мы делали), защёлка либо не срабатывает
вообще, либо срабатывает только один раз в самом конце — что и объясняло бы
"полное отсутствие реакции" при формально правильных данных на MOSI.

**Исправлено**:
- `Core/Src/main.c`: `LCD_Cmd`/`LCD_Param` заменены на `LCD_WriteReg`/
  `LCD_WriteData8` — каждая теперь САМА опускает и поднимает CS вокруг своего
  байта (или пары байт для данных). `LCD_WriteCmdParams` и `ILI9486_SetAddrWindow`
  переписаны как последовательность независимых CS-импульсов, точно как
  официальные `LCD_InitReg`/`LCD_SetWindow`. `ILI9486_SetAddrWindow` теперь
  сама полностью управляет CS для CASET/RASET/RAMWR и оставляет CS HIGH при
  выходе — вызывающий код обязан сам открыть НОВУЮ CS-сессию (`LCD_Begin()`)
  непосредственно перед потоком пикселей, а не держать её открытой с самого
  начала адресации.
- Обновлён порядок вызовов и в диагностическом `while(1)` в `main.c`, и в
  `TouchGFXHAL.cpp` (`touchgfxDisplayDriverTransmitBlock`): теперь
  `ILI9486_SetAddrWindow(...)` вызывается ПЕРВЫМ (сама пульсирует CS), и
  только ПОСЛЕ неё — `LCD_Begin()` перед циклом `LCD_WriteData()` пикселей.

**Статус: исправление внесено, ЕЩЁ НЕ ПРОВЕРЕНО на железе** — ждём следующей
прошивки и результата того же визуального теста (заливка/Display OFF/инверсия).

## 7.3 Дисплей №2 — TFTLCD-шилд для Arduino Mega2560 (ILI9481), без тача

### Роль в проекте
Второй дисплей задуман **не для управления, а для вывода графика обработанного звука**
— то есть визуализация (осциллограмма/спектр) в реальном времени. У этого шилда **нет
тачскрина** — это подтверждено официальной документацией шилда (в распиновке нет ни
одного сигнала тач-контроллера, только шина данных, SD-карта и SPI Flash).

### Почему выбран параллельный интерфейс FMC, а не SPI/сдвиговые регистры

Рассматривали три варианта передачи данных на этот экран:

1. **SPI + сдвиговые регистры (74HC595)** — экономит пины (нужно всего ~8 вместо 21), но
   каждое 16-битное слово требует сначала сдвинуть данные (16 тактов), потом защёлкнуть,
   потом дёрнуть WR — это добавляет задержку на каждый пиксель. Итоговая оценка: ~5-10
   FPS на полный экран вместо 30-60+ через нативный FMC. Отклонили, поскольку это
   дисплей для живого графика звука — рывки на нём будут не менее заметны, чем на
   анимации.
2. **Программный bit-bang через обычные GPIO** — самый медленный и самый прожорливый по
   CPU вариант, отклонили сразу.
3. **Аппаратный FMC (Flexible Memory Controller)** — встроенная периферия STM32H7,
   которая эмулирует классический интерфейс 8080 (тот самый, что использует ILI9481) на
   аппаратном уровне: контроллер сам генерирует WR/CS/адресную линию, данные выставляются
   на шину без участия CPU в цикле. В связке с DMA2D это даёт скорость на порядок выше
   остальных вариантов, при этом сама периферия на плате физически доступна и, как
   выяснилось при сверке по схеме, никак не задействована другими компонентами платы.

**Выбор:** FMC. Цена — больше физических пинов (21 вместо 8), но раз мы всё равно
проверили, что этих пинов хватает с запасом (см. 7.6), платить скоростью ради экономии
проводов смысла не было.

### Как определили физическую распиновку самого шилда

Изначально распиновка шилда была неизвестна (на дешёвых клонах шёлкография часто
отсутствует). Чтобы не гадать:

1. Шилд был физически вставлен в настоящую Arduino Mega2560, залит тестовый скетч на
   библиотеке UTFT
2. Экран заработал — значит, строка инициализации в скетче содержит реальные, рабочие
   номера пинов Mega
3. Строка `UTFT myGLCD(ILI9481, 38, 39, 40, 41);` — по документации UTFT это `(модель,
   RS, WR, CS, RST)`, то есть управляющие сигналы физически на пинах Mega D38-D41
4. Шина данных для этого класса шилдов (16-битные Mega/UTFT-шилды на ILI9481/HX8357/
   ILI9486) стандартно идёт на пинах **D22-D37** — это подтверждено независимо через
   исходники нескольких AVR-библиотек (`avrpins.h`, где явно прописано `D22→PA0 ...
   D29→PA7` и `D30→PC7 ... D37→PC0`, то есть шина данных = PORTA + PORTC Mega2560), и это
   совпало один-в-один с официальной распиновкой Mega2560, которую предоставил заказчик
   проекта
5. Поскольку шилд садится на Mega2560 физически всем корпусом сразу на все 4 ряда
   разъёмов — его собственные контакты зеркалят стандартную раскладку Mega. Реальный тест
   на живом экране подтвердил и правильность направления, и что RESET/3.3V с силового
   ряда Mega шилду для работы дисплея не требуются (они либо не разведены на шилде вовсе,
   либо используются только под SD-карту, которую в проекте не используем)

### Почему именно эти пины STM32, и что на них "мешало" изначально

Мы прошли по официальной принципиальной схеме платы (Altium SchDoc от WeAct) и
проверили КАЖДЫЙ нужный вывод на предмет конфликтов с уже впаянными компонентами самой
платы:

| Требуемый пин | Что там числилось занятым | Наше решение |
|---|---|---|
| PE10-PE15 | Онбордовый 0.96" TFT-экранчик (ST7735), подключается через отдельный шлейф J3 | Экран физически не подключаем (шлейф не втыкаем в J3) — линии полностью свободны, конфликта нет |
| PD6 (FMC_NE1) | Второй встроенный SPI Flash (U8), CS которого сидит именно на этом пине через перемычку **SB3** | **Перемычку не режем.** Флеш просто не инициализируем и не трогаем в прошивке пины его SPI-шины (PB3/PB4/PD7) — см. обоснование ниже |
| PD11 (FMC_A16) | Встроенный OSPI Flash (8 МБ), NCS которого подтянут резистором к 3.3В | OSPI просто не инициализируем в прошивке (CubeMX) — микросхема остаётся в неактивном высокоимпедансном состоянии, линия свободна для FMC без физического вмешательства |
| PD4 (в исходном варианте рассматривался под RD) | Механический контакт Card Detect слота microSD | Не критично в любом случае — просто металлический "лепесток" на GND, не электронный компонент. В итоговой схеме эта линия не понадобилась вовсе — RD у этого шилда физически не разведён (в его собственной документации сигнала RD нет вообще), поэтому FMC_NOE к шилду не подключаем |

**Ключевой вывод по этому разделу:** каждый "конфликт" решён без единого физического
вмешательства в плату — либо через простое неиспользование встроенной функции в
прошивке, либо через физическое отключение шлейфа необязательного компонента. Резать
ничего не потребовалось.

### Почему PD6 безопасно делить между LCD_CS и SPI Flash CS без разреза SB3

Перемычка SB3 соединяет PD6 одновременно с CS экрана (через FMC_NE1) и с CS второго
встроенного SPI Flash (U8). Если её не резать, при каждом обращении FMC к экрану
флеш-чип тоже будет получать сигнал "выбран" (CS в LOW). Это не создаёт риска по
следующим причинам:

1. **Флеш ничего не может сделать без тактов.** Чтобы SPI Flash реально выполнил команду
   (чтение/запись/стирание), ему нужны импульсы на линии CLK (PB3). Эта линия в прошивке
   никак не тактируется — флеш остаётся в состоянии "выбран, но ждёт команду", которая
   никогда не придёт.
2. **Линия MISO флеша (PB4) ни с чем не пересекается** в нашей распиновке — конфликтовать
   электрически не с чем, даже если флеш попытается что-то вывести на эту линию.
3. **Многократное переключение CS без тактовых импульсов — штатный режим** работы любой
   SPI-микросхемы флеш-памяти, никакого износа, повреждения данных или деградации чипа
   это не вызывает.
4. **Дополнительная электрическая нагрузка** от входа CS флеша на линии FMC_NE1 —
   единицы пикофарад, для драйвера FMC несущественно, на скорость и корректность работы
   экрана не влияет.

**Единственное условие:** в прошивке никогда не инициализировать SPI/OSPI-периферию под
этот флеш и не задействовать пины PB3/PB4/PD7 для чего-либо ещё. При соблюдении этого
условия оставлять перемычку SB3 нетронутой полностью безопасно.

## 7.4 Управление модулями ESP32 — I2C

Оба модуля ESP32-WROOM управляются с STM32 по **одной общей шине I2C** (I2C — шинный
протокол, оба модуля висят на одних и тех же линиях SCL/SDA, различаясь только адресом
устройства на шине).

### Конкретные пины

| Назначение | STM32 (нога) |
|---|---|
| I2C1_SCL (общая для обоих ESP32) | PB8 |
| I2C1_SDA (общая для обоих ESP32) | PB9 |

Эти пины — штатная дорожка I2C1, которую производитель платы развёл под управление
камерой (DCMI/SCCB). Поскольку камеру в проекте не используем, линия свободна по той же
логике, что и остальные "условно занятые" пины из раздела 7.3: конфликта нет, пока в
прошивке не инициализируется камера.

### Как STM32 отличает один ESP32 от другого

I2C сам по себе не различает устройства по проводам — все слейвы висят на одной
физической паре SCL/SDA. Различие идёт по **адресу устройства**, который каждый ESP32
объявляет в своей прошивке при инициализации (`Wire.begin(0x42)` для одного,
`Wire.begin(0x43)` для другого, например). STM32 как мастер обращается к конкретному
адресу — то есть к конкретному модулю — независимо от того, какой физический провод
куда идёт.

**Важно понимать:** обе платы ESP32-WROOM физически одинаковые, различие — исключительно
в том, какая прошивка на какую залита. Практические следствия:

1. Адрес назначается программно при прошивке каждого модуля и должен быть жёстко задан
   как константа в коде (например, `#define I2C_ADDR_BT_IN 0x42` и
   `#define I2C_ADDR_HP_OUT 0x43`)
2. STM32 в своей прошивке хранит оба адреса как именованные константы и обращается к
   нужному модулю по назначению ("отправить команду BT-приёмнику"), а не по порядку
   подключения
3. Платы рекомендуется **физически подписать сразу после прошивки** (стикер/маркер на
   текстолите с адресом и ролью) — иначе, будучи одинаковыми внешне, они неотличимы
   визуально, и легко перепутать при монтаже

## 7.5 Аудио-тракт — I2S/SAI (два независимых направления)

Поскольку звук идёт в двух независимых направлениях одновременно (приём от ESP32 №1 и
передача на ESP32 №2), под каждое направление выделяется отдельный аудио-интерфейс:

- **I2S RX** (приём необработанного звука от ESP32 №1, полученного по Bluetooth): BCLK,
  WS (LRCLK), SD — 3 линии
- **I2S TX** (передача обработанного звука на ESP32 №2, дальше на наушники): BCLK, WS,
  SD — 3 линии

Оба используют свободные GPIO STM32, не пересекающиеся с уже занятыми FMC/SPI2/I2C
линиями.

### ✅ Финальные пины (подтверждено датащитом STM32H723xE/G DS13313 Rev.4 + схемой WeAct)

| Канал | Сигнал | Пин STM32 | Периферия/AF | Разъём платы |
|---|---|---|---|---|
| RX (приём от ESP32 №1) | BCLK | **PE5** | SAI1_SCK_A, AF6 | P2, контакт 6 |
| RX | WS/LRCLK | **PE4** | SAI1_FS_A, AF6 | P2, контакт 5 |
| RX | SD (data in) | **PE6** | SAI1_SD_A, AF6 | P2, контакт 7 |
| TX (передача на ESP32 №2) | BCLK | **PC10** | SPI3_SCK / I2S3_CK, AF6 | P1, контакт 22 |
| TX | WS/LRCLK | **PA4** | SPI3_NSS / I2S3_WS, AF6 | P2, контакт 21 |
| TX | SD (data out) | **PC12** | SPI3_MOSI / I2S3_SDO, AF6 | P1, контакт 20 |

**Логика выбора**: RX целиком на **SAI1 Block A**, TX целиком на **SPI3 в режиме I2S**
(на STM32H723 нет отдельной периферии "I2S3" — это тот же SPI3, переведённый в I2S-режим;
такой режим поддерживают только SPI1/SPI3 на этом чипе, SPI4/5/6 — нет). SAI1 Block B не
подошёл — его пины (PF6-PF9) физически на порте F, который на этой плате вообще не выведен
ни на один разъём.

**Пересечения с уже занятыми блоками — нет** (не SPI2, не FMC, не I2C1). Все 6 пинов делят
линии только с периферией того же класса риска, что уже принят в плане ранее — камерой
DCMI (PE4/PE5/PE6/PC10/PA4) и слотом microSD (PC12): тот же принцип "не инициализируем эту
периферию в прошивке — линия свободна", никакой новой категории риска не вводится.

**Master/Slave** (не влияет на выбор пинов, чисто инженерная рекомендация): практичнее
сделать **STM32 master на обоих направлениях** (сам генерирует BCLK/WS для SAI1 и для
SPI3/I2S3), оба ESP32 — I2S slave. Так весь аудио-тракт синхронизирован от одного
тактового источника, без рассинхрона между двумя независимо свободнотекущими мастерами.

## 7.6 Итоговый бюджет пинов — хватает ли

| Блок | Сигналов |
|---|---|
| Дисплей №1 (Waveshare, SPI2 + тач) | 9 |
| Дисплей №2 (TFTLCD, FMC) | 20 |
| I2C (управление обоими ESP32) | 2 |
| I2S RX (звук от ESP32 №1) | 3 |
| I2S TX (звук на ESP32 №2) | 3 |
| **Итого** | **≈ 37** |

На платке STM32H723VGT6 Mini Core Board выведено **2 разъёма P1/P2, каждый "22×2" — то
есть 22 ряда по 2 пина = 44 контакта на разъём**. Итого физических позиций на обоих
разъёмах: **2 × 44 = 88**.

Из них не все — уникальные независимые GPIO: часть позиций на каждом разъёме дублирует
GND и питание (5V/3V3), выведенные в нескольких местах для удобства пайки, а не отдельные
сигналы. После вычета контактов, которые физически заняты фиксированными нуждами самой
платы и **не подлежат переносу** (кварц RTC, USB D+/D-, SWDIO/SWCLK для прошивки, кнопка,
дублирующиеся GND/питание) — свободного пространства с учётом всех произведённых
манипуляций (отказ от OSPI, отключение мини-экрана, отказ от резки SB3) оказывается
достаточно для полного бюджета в ~37 сигналов с большим запасом.

**Вывод: проект технически полностью реализуем на этой плате без доработки в виде
внешних микросхем-расширителей портов и без единой физической модификации самой платы.**
Все конфликты решены исключительно на уровне прошивки (не инициализируем ненужную
периферию) и физического отключения необязательного шлейфа мини-экрана.

## 7.7 Почему вообще выбран FMC, а не альтернативы — сводка решения

- **FMC** даёт аппаратную скорость записи в дисплей на порядок выше программных методов
  — критично для живого графика звука, где важна частота обновления кадра.
- Цена FMC — фиксированный набор пинов, который нельзя произвольно менять (в отличие от
  SPI/I2C/UART, где почти любая ножка подходит через альтернативные функции). Именно
  поэтому этому разделу было уделено больше всего внимания при сверке со схемой платы —
  ошибиться с FMC-пинами означало бы вообще не суметь развести шину.
- Все нужные FMC-пины физически выведены на разъёмы P1/P2 платы (это было отдельно
  проверено по официальной Altium-схеме WeAct Studio) — то есть ограничение "работаем
  только с тем, что выведено на GPIO-разъёмы, а не с ножками самого чипа" не помешало
  реализовать план.

## 7.8 Независимая проверка распайки по официальной схеме WeAct (после переноса плана)

Пользователь запросил отдельную независимую проверку: "все ли пины просчитаны нормально,
всё сходится, все выводы на плате есть, хватит ли, при жёстком условии — ничего не
отключать физически и дорожки не резать". Проверка выполнена отдельным агентом с прямым
доступом к первоисточнику — официальной схеме производителя, а не пересказом плана.

### Источник

**github.com/WeActStudio/WeActStudio.MiniSTM32H723**, файл
`Hardware/STM32H7xx SchDoc V12.pdf` (6 листов, Altium-экспорт, ревизия V1.2) — репозиторий
именно под STM32H723VGT6 (подтверждено наличием `stm32h723xx.h` в Examples). Прочитан
целиком. Ниже явно отмечено, что подтверждено этим документом буквально, а что —
достройка по общим знаниям STM32/FMC без датащита под рукой в моменте проверки.

### Главный вопрос — онбордовый мини-экран на PE10-PE15, нужно ли что-то отключать

**Подтверждено, план валиден.** Онбордовый 0.96" ST7735 подключается через **отдельный
разъём J3 (FPC0.5-SMT-8P, лист 6 схемы)** — гибкий шлейф-коннектор 0.5мм шаг, физически
отдельная деталь от платы, которую пользователь сам устанавливает (сгибает по линиям и
клеит на двусторонний скотч). По умолчанию экран может быть даже не наклеен/не вставлен.
Не подключать его = не "отключение" чего-либо на плате, а просто "не устанавливать
опциональный аксессуар". Условие пользователя не нарушается.

**Найдена неточность в исходном плане (в плюс пользователю):** реально мини-экран
занимает не 6 пинов (PE10-PE15), а **5 (PE10-PE14)**: LCD_LED→PE10(TIM), LCD_CS→PE11
(GPIO), LCD_SCL→PE12(SCK), LCD_WR_RS→PE13(GPIO), LCD_SDA→PE14(MOSI). **LCD_RESET у
мини-экрана не отдельный GPIO — жёстко подключён к общей цепи SYS_RESET** (та же, что и
NRST всего МК через супервизор MAX809T). **PE15 мини-экраном вообще не используется** —
свободен независимо от того, подключён шлейф J3 или нет. В плане (7.3) PE15 отдан под
FMC_D12 — с запасом, без проблем.

### Проверка конфликтов по схеме

| Пин(ы) плана | Что реально на них по схеме | Вердикт |
|---|---|---|
| PD6 (FMC_NE1 / LCD_CS шилда) | Лист 1: `SPIx_CS → PD6` через перемычку **SB3**, на второй флеш U8 (W25Q64, 8MB) | ✅ Подтверждено, SB3 не режется |
| PD11 (FMC_A16) | **Уточнено повторной проверкой (см. ниже) — это не NCS, а линия данных QSPI_BK1_IO1** встроенного флеша U7 (W25Q64) | ✅ Подтверждено — не инициализируем эту шину в прошивке, линия свободна |
| PB8/PB9 (I2C1) | Лист 1, явная стрелка: `I2C1_SCL → PB8`, `I2C1_SDA → PB9`. Эта же шина заведена на камерный разъём J2 (SCCB, DVP_SCL/DVP_SDA, лист 3) | ✅ Подтверждено, конфликт условный (только при физическом подключении камеры в J2 — не подключаем) |
| — | DCMI-камера реально занимает: PC6, PC7, PE0, PE1, PE4, PD3, PE5, PE6 (данные), PB7 (VSYNC), PA4 (HSYNC), PA6 (PCLK), PA8 (MCO/XCLK) — план вообще не использует ни один из этих пинов | ✅ Нет пересечений вообще |
| — | MicroSD (SDMMC1): PC8-PC12, PD2 — план их не трогает | ✅ Нет пересечений |
| PA13/PA14 | SWD-разъём P3 (4-контактный) — SWDIO=PA13, SWCLK=PA14 (через резисторы R2/R3 22Ω) | ✅ Подтверждено — это отдельный debug-header, не основные P1/P2 |
| PA15 | В схеме не задействован ни под что специальное (JTAG здесь не разводится — только SWD на PA13/PA14) | ✅ Свободен, план (RST шилда) корректен |

**Зарезервированные производителем пины** (не входят в бюджет свободных GPIO): PA13/PA14
(SWD), PA11/PA12 (USB D-/D+), NRST, BOOT0, PC13 (кнопка K1), PH0/PH1 (25МГц кварц),
PC14/PC15 (32.768кГц RTC-кварц), VBAT/VREF+/VCAP1-2 и все GND/3V3/5V-дубли. План их не
занимает — конфликтов нет.

### FMC-пины

Набор PD14/15, PD0/1, PE7-15, PD8-10 = FMC_D0-D15, PD11 = FMC_A16, PD5 = FMC_NWE,
PD6 = FMC_NE1 — стандартная, широко используемая в референс-дизайнах STM32 группа AF12
для 16-битной FMC-шины (та же, что в STM32F429 Discovery и большинстве проектов
"STM32+параллельный TFT"). Это высокая уверенность по опыту, но не построчно
перепроверенный по датащиту факт на момент этой проверки — рекомендация: при первой
генерации в CubeMX убедиться, что Pinout view не подсвечивает красным ни один из этих
пинов при выборе функции FMC (CubeMX сам не даст выбрать нерабочую AF).

**Отдельный нюанс — FMC_NOE (обычно PD4, "Read strobe")**: план сознательно не подключает
его к шилду (RD не разведён у самого шилда). PD4 всё равно может остаться зарезервирован
внутри CubeMX под режим NOR/PSRAM-банка FMC (даже без физического провода к экрану) —
просто никогда не будет реально дёргаться, т.к. прошивка только пишет (RAMWR), не читает
GRAM. Проблемы это не создаёт (PD4 и так не планировался под что-то ещё), но иметь в
виду — этот пин нельзя будет "освободить" под другие нужды (например I2S), если он
окажется занят конфигурацией FMC-банка в CubeMX.

### Уточнение по встроенному QSPI-флешу (найдено при подборе пинов I2S, см. 7.5)

Отдельная повторная проверка схемы (текстовое извлечение таблиц P1/P2, плюс сверка с
датащитом STM32H723xE/G DS13313 Rev.4) нашла явные стрелки "сигнал → пин" для всей шины
встроенного QSPI-флеша U7 (тот же W25Q64, что и на SPI-стороне U8 из раздела 7.3) —
предыдущая проверка знала только про один пин этой шины (PD11), реальный список шире:

| Сигнал QSPI-флеша | Пин STM32 | Подтверждение |
|---|---|---|
| QSPI_BK1_IO3 | PE2 | явная стрелка в схеме |
| QSPI_BK1_IO2 | PD12 | явная стрелка в схеме |
| QSPI_BK1_IO1 | **PD11** | явная стрелка в схеме (это тот пин, что в плане отдан под FMC_A16) |
| QSPI_BK1_IO0 | PB2 | явная стрелка в схеме |
| QSPI_CLK | PB6 | по тексту схемы, менее железно подтверждено, но пара с PB2 логична |
| QSPI_BK1_NCS | вероятно PD13 | НЕ подтверждено явной стрелкой — вывод сделан по соседству в разводке порта, это догадка, не факт первоисточника |

**Вывод не меняется, но становится точнее:** обоснование безопасности ("флеш не тактируется
в прошивке — значит делить с ним линию безопасно") распространяется на все 6 пинов этой
шины, а не только на PD11. Из плана этот список затрагивает только PD11 (FMC_A16) — остальные
5 пинов (PE2, PD12, PB2, PB6, вероятно PD13) в проекте вообще не используются ни под что, но
стоит держать в памяти, что они закреплены за встроенным флешем и не свободны для будущих
доработок без того же самого условия "не инициализировать эту периферию".

### Итог проверки

Все физические ограничения ("ничего не отключаю, дорожки не режу") выполняются планом
без нарушений — подтверждено официальной схемой производителя и датащитом ST, не
пересказом плана. Расхождение с оригинальным документом (в плюс пользователю): мини-экран
реально занимает 5 пинов, не 6 (см. выше), а линия PD11 — это данные QSPI-флеша (IO1), не
NCS, как считалось на первом проходе проверки — суть вывода ("безопасно, если не
инициализировать периферию") от этого не меняется.

**На данный момент план полностью закрыт**, включая финальные пины I2S/SAI (см. 7.5) —
все 37 сигналов проекта (SPI2: 9, FMC: 20, I2C1: 2, I2S RX: 3, I2S TX: 3) подтверждены как
физически доступные на разъёмах P1/P2 без единого конфликта и без физических модификаций
платы.
