# Аппаратная архитектура проекта на STM32H723VGT6 Mini Core Board

## 1. Общая картина проекта

Центральный контроллер — **STM32H723VGT6 Mini Core Board** (WeAct Studio, LQFP100, Cortex-M7 до 550 МГц). К нему подключаются:

- **2 дисплея** (один — тачскрин, второй — только вывод графики)
- **2 модуля ESP32-WROOM** — один принимает звук по Bluetooth и передаёт его в STM32, второй получает обработанный звук от STM32 и выводит на наушники

STM32 в этой схеме — центр обработки: принимает звук от ESP32 №1, применяет эффекты, отображает график на втором дисплее, принимает команды управления с тачскрина, и отправляет обработанный звук на ESP32 №2.

**Важное техническое ограничение, определившее весь дальнейший план:** плата STM32H723VGT6 распаяна в компактном модуле (LQFP100), выводы самого контроллера физически недоступны для пайки — работать можно только с тем, что производитель вывел на два ряда 2×22 GPIO-разъёмов (P1 и P2). Поэтому весь подбор пинов ниже — это подбор именно по доступным физическим контактам на плате, а не по датащиту чипа напрямую.

## 2. Дисплей №1 — Waveshare 3.5", резистивный тач, по SPI

### Предыстория
По изначальному плану в проекте должен был стоять **один экран, работающий по SPI, с тачскрином** — именно такую роль в системе играет Waveshare 3.5" 480×320. Он и был подключён первым, замену пришлось делать позже — второй экран (см. ниже) появился в проекте отдельно, как дополнительный вывод для графика звука, а не как замена этого SPI-тач-экрана.

### Роль в проекте
- Единственный экран с сенсорным управлением
- Через него идёт управление эффектами обработки звука

### Занятые контакты (SPI2 + управление)

## 3. Дисплей №2 — TFTLCD-шилд для Arduino Mega2560 (ILI9481), без тача

### Роль в проекте
Второй дисплей задуман **не для управления, а для вывода графика обработанного звука** — то есть визуализация (осциллограмма/спектр) в реальном времени. У этого шилда **нет тачскрина** — это подтверждено официальной документацией шилда (в распиновке нет ни одного сигнала тач-контроллера, только шина данных, SD-карта и SPI Flash).

### Почему выбран параллельный интерфейс FMC, а не SPI/сдвиговые регистры

Рассматривали три варианта передачи данных на этот экран:

1. **SPI + сдвиговые регистры (74HC595)** — экономит пины (нужно всего ~8 вместо 21), но каждое 16-битное слово требует сначала сдвинуть данные (16 тактов), потом защёлкнуть, потом дёрнуть WR — это добавляет задержку на каждый пиксель. Итоговая оценка: ~5-10 FPS на полный экран вместо 30-60+ через нативный FMC. Отклонили, поскольку это дисплей для живого графика звука — рывки на нём будут не менее заметны, чем на анимации.
2. **Программный bit-bang через обычные GPIO** — самый медленный и самый прожорливый по CPU вариант, отклонили сразу.
3. **Аппаратный FMC (Flexible Memory Controller)** — встроенная периферия STM32H7, которая эмулирует классический интерфейс 8080 (тот самый, что использует ILI9481) на аппаратном уровне: контроллер сам генерирует WR/CS/адресную линию, данные выставляются на шину без участия CPU в цикле. В связке с DMA2D это даёт скорость на порядок выше остальных вариантов, при этом сама периферия на плате физически доступна и, как выяснилось при сверке по схеме, никак не задействована другими компонентами платы.

**Выбор:** FMC. Цена — больше физических пинов (21 вместо 8), но раз мы всё равно проверили, что этих пинов хватает с запасом (см. раздел 5) — платить скоростью ради экономии проводов смысла не было.

### Как определили физическую распиновку самого шилда

Изначально распиновка шилда была неизвестна (на дешёвых клонах шёлкография часто отсутствует). Чтобы не гадать:

1. Шилд был физически вставлен в настоящую Arduino Mega2560, залит тестовый скетч на библиотеке UTFT
2. Экран заработал — значит, строка инициализации в скетче содержит реальные, рабочие номера пинов Mega
3. Строка `UTFT myGLCD(ILI9481, 38, 39, 40, 41);` — по документации UTFT это `(модель, RS, WR, CS, RST)`, то есть управляющие сигналы физически на пинах Mega D38-D41
4. Шина данных для этого класса шилдов (16-битные Mega/UTFT-шилды на ILI9481/HX8357/ILI9486) стандартно идёт на пинах **D22-D37** — это подтверждено независимо через исходники нескольких AVR-библиотек (`avrpins.h`, где явно прописано `D22→PA0 ... D29→PA7` и `D30→PC7 ... D37→PC0`, то есть шина данных = PORTA + PORTC Mega2560), и это совпало один-в-один с официальной распиновкой Mega2560, которую предоставил заказчик проекта
5. Поскольку шилд садится на Mega2560 физически всем корпусом сразу на все 4 ряда разъёмов — его собственные контакты зеркалят стандартную раскладку Mega. Реальный тест на живом экране подтвердил и правильность направления, и что RESET/3.3V с силового ряда Mega шилду для работы дисплея не требуются (они либо не разведены на шилде вовсе, либо используются только под SD-карту, которую в проекте не используем)

### Почему именно эти пины STM32, и что на них "мешало" изначально

Мы прошли по официальной принципиальной схеме платы (Altium SchDoc от WeAct) и проверили КАЖДЫЙ нужный вывод на предмет конфликтов с уже впаянными компонентами самой платы:

| Требуемый пин | Что там числилось занятым | Наше решение |
|---|---|---|
| PE10-PE15 | Онбордовый 0.96" TFT-экранчик (ST7735), подключается через отдельный шлейф J3 | Экран физически не подключаем (шлейф не втыкаем в J3) — линии полностью свободны, конфликта нет |
| PD6 (FMC_NE1) | Второй встроенный SPI Flash (U8), CS которого сидит именно на этом пине через перемычку **SB3** | **Перемычку не режем.** Флеш просто не инициализируем и не трогаем в прошивке пины его SPI-шины (PB3/PB4/PD7) — см. обоснование ниже |
| PD11 (FMC_A16) | Встроенный OSPI Flash (8 МБ), NCS которого подтянут резистором к 3.3В | OSPI просто не инициализируем в прошивке (CubeMX) — микросхема остаётся в неактивном высокоимпедансном состоянии, линия свободна для FMC без физического вмешательства |
| PD4 (в исходном варианте рассматривался под RD) | Механический контакт Card Detect слота microSD | Не критично в любом случае — просто металлический "лепесток" на GND, не электронный компонент. В итоговой схеме эта линия не понадобилась вовсе — RD у этого шилда физически не разведён (в его собственной документации сигнала RD нет вообще), поэтому FMC_NOE к шилду не подключаем |

**Ключевой вывод по этому разделу:** каждый "конфликт" решён без единого физического вмешательства в плату — либо через простое неиспользование встроенной функции в прошивке, либо через физическое отключение шлейфа необязательного компонента. Резать ничего не потребовалось.

### Почему PD6 безопасно делить между LCD_CS и SPI Flash CS без разреза SB3

Перемычка SB3 соединяет PD6 одновременно с CS экрана (через FMC_NE1) и с CS второго встроенного SPI Flash (U8). Если её не резать, при каждом обращении FMC к экрану флеш-чип тоже будет получать сигнал "выбран" (CS в LOW). Это не создаёт риска по следующим причинам:

1. **Флеш ничего не может сделать без тактов.** Чтобы SPI Flash реально выполнил команду (чтение/запись/стирание), ему нужны импульсы на линии CLK (PB3). Эта линия в прошивке никак не тактируется — флеш остаётся в состоянии "выбран, но ждёт команду", которая никогда не придёт.
2. **Линия MISO флеша (PB4) ни с чем не пересекается** в нашей распиновке — конфликтовать электрически не с чем, даже если флеш попытается что-то вывести на эту линию.
3. **Многократное переключение CS без тактовых импульсов — штатный режим** работы любой SPI-микросхемы флеш-памяти, никакого износа, повреждения данных или деградации чипа это не вызывает.
4. **Дополнительная электрическая нагрузка** от входа CS флеша на линии FMC_NE1 — единицы пикофарад, для драйвера FMC несущественно, на скорость и корректность работы экрана не влияет.

**Единственное условие:** в прошивке никогда не инициализировать SPI/OSPI-периферию под этот флеш и не задействовать пины PB3/PB4/PD7 для чего-либо ещё. При соблюдении этого условия оставлять перемычку SB3 нетронутой полностью безопасно.

## 4. Управление модулями ESP32 — I2C

Оба модуля ESP32-WROOM управляются с STM32 по **одной общей шине I2C** (I2C — шинный протокол, оба модуля висят на одних и тех же линиях SCL/SDA, различаясь только адресом устройства на шине).

### Конкретные пины

| Назначение | STM32 (нога) |
|---|---|
| I2C1_SCL (общая для обоих ESP32) | PB8 |
| I2C1_SDA (общая для обоих ESP32) | PB9 |

Эти пины — штатная дорожка I2C1, которую производитель платы развёл под управление камерой (DCMI/SCCB). Поскольку камеру в проекте не используем, линия свободна по той же логике, что и остальные "условно занятые" пины из раздела 3: конфликта нет, пока в прошивке не инициализируется камера.

### Как STM32 отличает один ESP32 от другого

I2C сам по себе не различает устройства по проводам — все слейвы висят на одной физической паре SCL/SDA. Различие идёт по **адресу устройства**, который каждый ESP32 объявляет в своей прошивке при инициализации (`Wire.begin(0x42)` для одного, `Wire.begin(0x43)` для другого, например). STM32 как мастер обращается к конкретному адресу — то есть к конкретному модулю — независимо от того, какой физический провод куда идёт.

**Важно понимать:** обе платы ESP32-WROOM физически одинаковые, различие — исключительно в том, какая прошивка на какую залита. Практические следствия:

1. Адрес назначается программно при прошивке каждого модуля и должен быть жёстко задан как константа в коде (например, `#define I2C_ADDR_BT_IN 0x42` и `#define I2C_ADDR_HP_OUT 0x43`)
2. STM32 в своей прошивке хранит оба адреса как именованные константы и обращается к нужному модулю по назначению ("отправить команду BT-приёмнику"), а не по порядку подключения
3. Платы рекомендуется **физически подписать сразу после прошивки** (стикер/маркер на текстолите с адресом и ролью) — иначе, будучи одинаковыми внешне, они неотличимы визуально, и легко перепутать при монтаже

## 5. Аудио-тракт — I2S/SAI (два независимых направления)

Поскольку звук идёт в двух независимых направлениях одновременно (приём от ESP32 №1 и передача на ESP32 №2), под каждое направление выделяется отдельный аудио-интерфейс:

- **I2S RX** (приём необработанного звука от ESP32 №1, полученного по Bluetooth): BCLK, WS (LRCLK), SD — 3 линии
- **I2S TX** (передача обработанного звука на ESP32 №2, дальше на наушники): BCLK, WS, SD — 3 линии

Оба используют свободные GPIO STM32, не пересекающиеся с уже занятыми FMC/SPI2/I2C линиями.

## 6. Итоговый бюджет пинов — хватает ли

| Блок | Сигналов |
|---|---|
| Дисплей №1 (Waveshare, SPI2 + тач) | 9 |
| Дисплей №2 (TFTLCD, FMC) | 20 |
| I2C (управление обоими ESP32) | 2 |
| I2S RX (звук от ESP32 №1) | 3 |
| I2S TX (звук на ESP32 №2) | 3 |
| **Итого** | **≈ 37** |

На платке STM32H723VGT6 Mini Core Board выведено **2 разъёма P1/P2, каждый "22×2" — то есть 22 ряда по 2 пина = 44 контакта на разъём**. Итого физических позиций на обоих разъёмах: **2 × 44 = 88**.

Из них не все — уникальные независимые GPIO: часть позиций на каждом разъёме дублирует GND и питание (5V/3V3), выведенные в нескольких местах для удобства пайки, а не отдельные сигналы. После вычета контактов, которые физически заняты фиксированными нуждами самой платы и **не подлежат переносу** (кварц RTC, USB D+/D-, SWDIO/SWCLK для прошивки, кнопка, дублирующиеся GND/питание) — свободного пространства с учётом всех произведённых манипуляций (отказ от OSPI, отключение мини-экрана, отказ от резки SB3) оказывается достаточно для полного бюджета в ~37 сигналов с большим запасом.

**Вывод: проект технически полностью реализуем на этой плате без доработки в виде внешних микросхем-расширителей портов и без единой физической модификации самой платы.** Все конфликты решены исключительно на уровне прошивки (не инициализируем ненужную периферию) и физического отключения необязательного шлейфа мини-экрана.

## 7. Почему вообще выбран FMC, а не альтернативы — сводка решения

- **FMC** даёт аппаратную скорость записи в дисплей на порядок выше программных методов — критично для живого графика звука, где важна частота обновления кадра.
- Цена FMC — фиксированный набор пинов, который нельзя произвольно менять (в отличие от SPI/I2C/UART, где почти любая ножка подходит через альтернативные функции). Именно поэтому этому разделу было уделено больше всего внимания при сверке со схемой платы — ошибиться с FMC-пинами означало бы вообще не суметь развести шину.
- Все нужные FMC-пины физически выведены на разъёмы P1/P2 платы (это было отдельно проверено по официальной Altium-схеме WeAct Studio) — то есть ограничение "работаем только с тем, что выведено на GPIO-разъёмы, а не с ножками самого чипа" не помешало реализовать план.
